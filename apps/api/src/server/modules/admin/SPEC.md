# Independent administrator account and authentication boundary

This implements the approved identity boundary and the character content/publish boundary of the web-admin rollout, not a new user-authentication model. Migrations 0013–0018 and historical typed actors remain additive. Miniapp `verifyAuth`, payments and streaming are independent.

Product scope is frozen in `docs/specs/2026-10-31-web-admin-spec.md` (revision 3). Batch 1 shipped the identity/account/session boundary plus the Chinese admin shell; batch 2 ships the character content model (`content_versions` drafts, the single published pointer, immutable publish), the character admin flows, session search/paginated transcript with per-turn version attribution, and the accepted-turn version pin. Batch 3 ships user operations (search, profile, ban/unban, AC-11), quota package maintenance, the manual wallet adjustment console (AC-13/AC-14) and **local media upload/reuse** (`0018_media_assets`, content-addressed files under `MEDIA_ROOT`, `POST /api/admin/media`, `GET /api/media/[id]`, the avatar/cover picker on the character forms and the cover-only `/admin/scripts` pages). Batch 3 step 6 adds the audit-recovery entry points (script and model publish, on top of the existing character and wallet actions) and records AC-12 channel reconciliation as BLOCKED (see below). Batch 3 step 7 makes the character list scale-safe (count + bounded page + keyed per-row reads, validated search, measured index decision) and records the mobile emergency-unpublish path (AC-18). Character deletion, order reconciliation, the script *text* editor (title/description/world-setting — only the cover ships here), media garbage collection, object storage/CDN, and a general audit-recovery console remain later batches. Implementation status is PARTIAL: local verification uses real PostgreSQL/HTTP/browser, the Node 20 tools image and a local Caddy configuration; production HTTPS/deployment, real miniapp devices, payment channels and LLM providers are not covered.

## Responsibilities and contracts

- `passwords.ts`: async Node scrypt, `scrypt$v1$32768$8$1$<16-byte hex salt>$<64-byte hex output>`, maxmem 64 MiB. Only this exact cost/format is verifiable. Maximum four expensive operations per process; no waiting queue, overload 503. Passwords are 15–128 Unicode codepoints, untrimmed and unnormalized, rejecting common weak values; all credential-setting services share validation.
- `accounts.ts`: normalized-email uniqueness, safe account projection (no hash/version), protected bootstrap/recovery, account lifecycle and current-actor validation. Ordinary creation is strict `{email,password}`, active/restricted/nonprotected. No deletion or reactivation HTTP interface. Only protected self can change email with current password. No self-disable or protected reset/disable by administrators. Recovery explicitly targets an existing UUID and retains protection.
- `authentication.ts`: `AdminIdentity = {adminAccountId,credentialVersion,sessionId,expiresAt,account}`. `loginAdmin({email,password,clientIp})` returns `{token,identity}` internally; HTTP never serializes this internal result. Account mutation services require this identity, not client actors or user IDs.
- `security.ts`: exact Origin + JSON + `X-Admin-Request: 1` on every admin write, private/no-store serializers, safe internal return paths, cookie helpers and persistent login budgets. The **only** non-JSON body is the media upload, and it is a *named body kind* (`media_upload`) that `validateAdminWrite` accepts exclusively on `/api/admin/media` — a caller that asks for it on any other path is `403 admin_csrf_failed`, so the exception cannot be widened by passing a content-type list. Email 5/15m, trusted IP 30/15m, global 60/min, consumed atomically in sorted key order before hashing. Denials have positive Retry-After. Stable keys hash email/IP. Cleanup deletes at most 100 expired rows per attempt using indexed expiry/skip-locked; denied attempts saturate counts.
- API `verifyAdminAuth` and SSR `requireAdminPageAuth` use the same token resolver. Full access is default; explicit restricted allowance only for session self-check, own-password change and logout. The change-password page opts in only to display the current identity; no business page or query may use it. SSR returns null without querying protected data on denied/unavailable identity and opts out of caching.
- Old JWT (including whitelist and development bypass), Basic, `admin_session`, and `x-admin-session` never grant admin identity. Historical session creation/revocation remains only for migration regression tests; no legacy resolver is exported or used for authentication.

## Character content versions and the publish boundary

`content_versions` with `entityType='character'` stores every immutable draft and published snapshot as one row (`entityId`, `versionNo`, `status`, `contentHash`, `payload`). `characters.published_version_id` (FK to that table, `0014`) is the single published pointer a chat turn reads; at most one `published` row may exist per `(entity_type, entity_id)` (partial unique index `content_versions_entity_published_unique`). A save inserts a new draft and supersedes the previous draft in one transaction; publish re-validates the bound version, freezes the server-derived `scriptSnapshot` into it, flips display rows and the pointer atomically, and writes a `publish_tasks` row plus an `audit_pending` intent. Unpublish only sets `characters.status='inactive'`: versions, the pointer, tasks and audit stay. Drafts never carry `scriptSnapshot`, and neither the client nor a draft may supply it.

Baselines: a save carries exactly one of `versionId` or `expectedUpdatedAt` (both or neither is `400 admin_input_invalid`); a stale baseline is `409 character_draft_conflict`, never a silent write. `agentId` is system-owned once stored (`409 character_agent_id_system_owned`), and a published character cannot change `scriptId` (`409 character_script_change_requires_new_character`) — re-binding a role requires a new character. The runtime prerequisite for a turn (an enabled model tier with a published model-profile version) is reported as preflight and **never** blocks publishing: a missing model-profile version only means new turns will be refused with `model_profile_unavailable`.

## Local media assets (`0018`)

Avatars and script covers are **local files, content-addressed** — no object storage, no CDN, no new service or subdomain. `media_assets(id uuid pk, content_hash text unique, mime text, byte_size int, width int, height int, original_name text, created_by_admin_account_id uuid fk→admin_accounts, created_at timestamptz)` with checks on the mime allowlist, 1…5 242 880 bytes and 1…4096 px per side. `original_name` is always `NULL`: the upload contract is a raw body with no filename, so no client name can ever reach storage, the response or an audit summary. Rows are immutable; `content_hash` format is validated in the storage layer on purpose (a corrupted row must fail closed at read time instead of being impossible to create).

Bytes live at `<MEDIA_ROOT>/<hash[0:2]>/<hash>.<png|jpg|webp>`. Only a validated 64-hex hash and an extension derived from the mime allowlist participate in the path, and the resolved path is re-checked to stay inside the resolved root; a hostile stored row therefore 404s instead of being read. Writes go through a unique temp file in the same directory → `fsync` → `rename`, so a reader never sees a partial file.

`POST /api/admin/media` is a raw-body upload, in this order: guard/CSRF → bounded read (`MEDIA_MAX_BYTES`, the stream is cancelled the moment the limit is crossed) → empty check → magic-byte sniff → header-only dimension parse (1…4096 px per side, ratio ≤ 20:1) → sha256 → lookup by hash (identical bytes **reuse** the row/URL and write no second audit) → write file → insert row + `admin.media.upload` audit in one transaction. The declared `Content-Type` is CSRF material only; the stored type is the sniffed one (a GIF declared as PNG is `415 media_type_unsupported`). Failures are `415 media_type_unsupported`, `413 media_too_large`, `400 media_dimensions_invalid`, `503 media_store_unavailable`, 401 unauthenticated, 403 CSRF; the audit summary carries the content hash and the parsed facts, never bytes, a filename or a path.

**The write order is the invariant.** The file is written before the row is inserted, so a row without a file cannot be created. A failed insert deliberately leaves the just-written file in place: an orphan file is harmless (delivery resolves bytes through a row) and self-healing (the next upload of the same bytes inserts the row and reuses the file), whereas deleting it could race a concurrent identical upload that already observed the file and then inserts its own row.

Nothing in this capability ever deletes or overwrites an asset: replacing an image mints a new asset and a new URL, so a published `content_versions` payload that still points at the old URL keeps working. `GET /api/media/[id]` is public (the miniapp renders it cross-origin), takes no path parameter, no listing and no content negotiation, and answers with the stored mime, `Content-Length`, a strong `ETag` (`"<sha256>"`), `Cache-Control: public, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff`; matching `If-None-Match` is `304`; an unknown/malformed id, a row whose file is gone, or an invalid stored path is `404 media_not_found` (`no-store`). URLs are absolute — `${ADMIN_ORIGIN}/api/media/<uuid>` — because the miniapp loads them from a different origin; the origin comes from validated config, never from a request `Host`.

**Deployment requirement:** `MEDIA_ROOT` must sit on a persistent named volume, and that volume must be backed up together with PostgreSQL. `docker-compose.yml` mounts `media_data:/app/data/media` for the `api` service and sets `MEDIA_ROOT=/app/data/media` explicitly (local development keeps the relative `./data/media` default); `scripts/deploy-config.test.mjs` fails if the mount, the volume declaration or the explicit `MEDIA_ROOT` is dropped, or if the two disagree. Without it a container recreate wipes the files while the `media_assets` rows survive, so every already-published avatar/cover becomes a permanent `404` and recovery needs a re-upload (new rows, new URLs) plus re-publishing.

Known, deliberate limits: no re-encode/resize/thumbnail, no GC or quota (disk grows with every distinct upload by design), and validation reads image headers only — a payload with a valid signature and dimension header is accepted even if the pixel stream is truncated, which `nosniff` and the image-only allowlist (no SVG) mitigate but do not eliminate.

## Derived FastClaw base context (`0016`, `0017`, plan W)

The published PG version is the single persona source. FastClaw keeps its runtime context assembly unchanged (a roleplay turn still reads SOUL.md + IDENTITY.md + USER.md + memory + the output guards), so those three files are a **derived, versioned cache**: publish regenerates them from the version it just activated, writes them through the setup API (`GET`/`PUT /api/agents/{id}/system-files/{name}`, `Authorization: Bearer`, agent id in the path, bounded 5s per request, no retries — the operation is idempotent by content) and records one `agent_context_versions` row. `0016_agent_context_versions.sql` adds that table (unique `(agent_id, content_hash)` so identical bytes never duplicate, `snapshot` = the three rendered files + per-file hashes + character counts, `source` `publish|manual|startup`, nullable `captured_by_admin_account_id`, the originating `content_version_id`/`content_version_no`) and a nullable `chat_turn_snapshots.agent_context_version_id`.

The renderer is server-side and single (`agent-context/render.ts`); `scripts/provision-roleplay-agents.mjs` keeps owning the deploy path and a parity test renders the same characters through both and asserts byte equality, so publish and provisioning cannot drift. Recording is hash-deduped and immutable; the per-agent `b#` badge is a derived ordinal, not an id.

**Which record is current is an explicit pointer, not an ordering.** `0017_agent_current_context.sql` adds `agent_current_context(agent_id PRIMARY KEY, version_id REFERENCES agent_context_versions ON DELETE CASCADE, updated_at)` and backfills one row per agent from the newest capture (replay-safe). Recording is hash-deduped, so publishing A → B → A re-uses the OLD A row with its old `created_at`; `max(created_at)` would then report drift against B while the runtime holds A, no rebuild could clear it, and new turns would pin B. The pointer is written in the SAME transaction as the record and only after the write was verified, so the record insert and "this is what FastClaw holds" can never disagree. Drift, the panel badge (`b#` of the current row), `matchesPublished` and turn attribution all read the pointer; `agent_context_versions` stays append-only history.

**Writes are read back before anything is claimed.** After the three PUTs the sync re-reads all three files and compares exact bytes (and the combined hash). Any mismatch — a PUT that answered 200 without the bytes being visible afterwards — is `failed`/`write_not_verified[:<file>]`, records nothing and never repoints current. `written` is true only when all three PUTs landed; a partial write is `false`.

The read-back proves only that the bytes are visible to the credential in use: FastClaw's setup API scopes both GET and PUT by the authenticated user, so a credential that is not the agent owner writes and reads the same wrong row and still compares equal. Keeping `FASTCLAW_API_KEY` resolvable to the agent's `agents.user_id` is therefore an operational requirement, not something this check can detect.

Syncs are serialized per agent with `pg_advisory_xact_lock(hashtext(agent_id))` and the published source is re-read inside that lock, so two concurrent publishes can never leave a stale current version.

Publish is never failed, rolled back or downgraded by this step: `publishCharacter` returns `baseContext` with `synced | unchanged | pending | failed` (`pending` = FastClaw unreadable, nothing written or recorded, last good record kept; `failed` = a rejected write, a failed read-back, or a failed record — each with its own copy: 写入失败 / 校验失败 / 未记录). The accepted-turn attribution reads the agent's CURRENT recorded version in the accept transaction (one local read, no cross-service call) and stores NULL when nothing was recorded — never backfilled, never inferred. Drift is `GET /characters/:id/base-context` (current record vs the live files: `in-sync | drifted | unavailable | unrecorded`; `unavailable` is never reported as synced) and the rebuild is `POST /characters/:id/base-context` (audited `admin.character.base_context.rebuild`), which overwrites a FastClaw-console hand edit and repoints current even when the bytes match an older row. The admin UI states both facts separately (`基础上下文：b# · 时间 · 状态`, `控制台已被手改，与已发布版本不一致`, `基础上下文未记录`) and never renders persona text or the captured file bytes. `startup` remains a reserved source value with no caller.

## Scale-friendly character list and mobile emergency unpublish (AC-18)

`listAdminCharacters({query,status,page,pageSize})` is now a **bounded page**, not a full-table assembly. The 1000-character baseline is the acceptance scale, so the read is `count` + page + three keyed per-row reads, none of them per character:

- **page** — `characters LEFT JOIN character_prompts` with `ORDER BY sort_order, name, id`, `LIMIT pageSize OFFSET offset`. No other join, so the limit really bounds the statement. The ordering is the documented managed order with an id tiebreaker, so neighbouring pages cannot overlap or reorder between reads.
- **count** — `SELECT count(*) FROM characters WHERE <same predicate>`; the page facts (`total`, `page`, `pageSize`) come from here, never from the number of rendered rows.
- **published version** — primary-key lookups for the page's `published_version_id` pointers (≤ `pageSize` rows). A pointer that names another entity's version resolves to nothing, so such a row honestly reports `线上版本缺失`.
- **newest version** — one `DISTINCT ON (entity_id) … ORDER BY entity_id, version_no DESC` over the page ids, so a character's superseded drafts never widen the page. `content_versions_entity_version_unique` serves the ordering.
- **last publish task** — one `DISTINCT ON (entity_id)` over the page ids ordered by `created_at DESC, id DESC`; a growing task history still yields one row per character.

Measured statement counts (real PG, 1000 seeded characters): **5** statements for a page that contains a published character (page, count, published pointers, newest versions, last tasks), **4** when no row on the page has a published pointer, **2** for an empty page. A 100-row page costs the same as a 20-row page, which is what makes the absence of N+1 testable.

**Search** is one trimmed term matched case-insensitively as a substring against the character name, the agent id and the bound script title (`EXISTS (SELECT 1 FROM scripts …)`, not a join, so one character can never appear twice). `%`, `_` and `\` in the operator's term are escaped and matched literally (`escapeLikeTerm`, shared with user search). The term is capped at 128 characters, `status` accepts only the two stored values, and the page must be an integer ≥ 1; an unusable value is a `400` with Chinese copy (API) or a warning that is *not applied* (page) — a typo never silently widens a 1000-row list. Blank term = no filter.

**Indexes: none added, deliberately.** `EXPLAIN (ANALYZE, BUFFERS)` on the seeded 1000-character baseline (2000 content versions, 3000 publish tasks) shows: page 1.03 ms and search 1.30 ms as `Seq Scan on characters` + `top-N heapsort`; count 0.88 ms; published pointers 0.07 ms (`Bitmap Index Scan` on `content_versions_pkey`); newest versions 0.10 ms (`Index Scan` on `content_versions_entity_status_idx`); last publish task 0.46 ms as `Seq Scan on publish_tasks` (60 rows kept of 3000). At that size no statement is a bottleneck, so an index would be speculative. The one to watch is the task read: re-run the same measurement after one order of magnitude more `publish_tasks` (measured 4.6 ms at 30 000 tasks) and add `publish_tasks (entity_type, entity_id, created_at DESC, id DESC)` only if it becomes the dominant statement. A trigram index for the substring search would need the `pg_trgm` extension and is not justified at this baseline either.

**Mobile emergency unpublish (§4.1 手机至少支持查看和紧急下架).** The list's first cell — the only cell visible at 390px without scrolling the table — carries a `下架（需确认）` link (`data-character-unpublish-entry`) for a live character, pointing at `/admin/characters/[id]/preview#emergency-unpublish`; the 操作 column still holds 编辑/预览/玩家会话 for wide screens. The preview page's 发布与下架 section is that anchor target (`id="emergency-unpublish"`, `scroll-margin-top: 16px`) and the header carries a one-line shortcut to it (`data-unpublish-shortcut`). The confirmation is unchanged and honest: a checkbox whose copy states that unpublish stops public visibility and new sessions while accepted in-flight turns finish on the old version and history, versions and publish records are kept. Nothing about it is hidden in a disclosure or disabled for a live character — the only gate is the unticked box. Measured in Chromium at 390×844 with the real console shell and `admin.css`: document scroll width equals the viewport (no page-level horizontal scroll; the table is the only local horizontal scroller, 698 vs 341 px), the list entry sits at x 29–120 fully on screen while the 操作 column link is at x 577 (off screen), the preview page has no horizontal scroller at all, and after clicking the shortcut the page scrolls to the panel (panel top 104, action button at 62×42 inside the viewport). 1440 and 1024 were re-measured the same way: no body scroll, the table fits without a scroller.

## User operations: search, profile and ban/unban (AC-11)

`/users.ts` owns the *player* namespace only. Administrator identity lives in `admin_accounts` inside the independent admin boundary, so a player whose UUID equals an administrator's account id is a different row in a different table: banning that player never disables, resets or logs out the administrator (tested through `verifyAdminAuth` with a real session).

`listAdminUsers({query,status,page,pageSize})` matches one trimmed term three ways — nickname substring (`ILIKE`), openid prefix (`LIKE`, wildcard characters in the operator's term are escaped and therefore literal) and user-id text prefix (a pasted full UUID matches exactly) — and combines it with the status filter. Ordering is `created_at DESC, id DESC`, so a bounded page never reorders between reads. Each row carries `id, nickname, status, createdAt, balancePoints, sessionCount, lastMessageAt`; the aggregates are correlated scalar subqueries in the page statement, so a page of 50 users is one page statement plus one count statement (no N+1), and a player with no wallet row reports `0` rather than a missing value.

`getAdminUser(id)` returns the profile (`nickname, avatarUrl, status, createdAt, updatedAt`, plus a masked `openidPreview` — the raw openid is a login identifier and is never returned), the wallet summary (`balancePoints`, `totalRechargedPoints`, `totalConsumedPoints`, or `exists:false` with zeros), usage totals (`sessionCount`, `messageCount`, `lastMessageAt`, `lastSessionAt`) and the 10 most recent sessions as ids with display context (character name, mode, status, message count, timestamps) so an operator can jump into the existing chat history. No persona prompt, chat body or credential material is selected.

`setAdminUserStatus(actor,id,status,requestId?)` accepts only `active ↔ banned`. One transaction locks the user row (`FOR UPDATE`), and: a missing row is `404`, a malformed id or unknown status is `400` before any write; a status that already matches returns `changed:false` and writes nothing; a real transition updates `users.status`/`updated_at` and appends the audit event within the same transaction — `admin.user.ban` / `admin.user.unban`, `objectType='user'`, `objectId=<player>`, the authenticated administrator as actor, `summary {from,to}` — and a failed audit insert rolls the write back. Because only a real transition can reach the audit insert and the row lock serializes concurrent duplicates into one transition plus no-ops, repeated identical calls add no second audit row without needing a dedupe key; a later ban after an unban is a new event.

Enforcement is the pre-existing user authentication: `verifyAuth` already refuses a JWT whose `users.status` is not `active`, so an already-issued credential stops authorizing new user business requests immediately and works again after the unban. Banning changes no wallet balance, inserts no wallet transaction, and deletes no user, session or message.

Routes: `GET /users` (`q`, `status`, `page`, `pageSize`; unknown status and an over-long term are `400` with Chinese copy), `GET /users/:id`, `PATCH /users/:id` with the strict body `{status:'active'|'banned'}` (a client `actor`, a wallet field or any other key is `400 admin_input_invalid`). Both pages guard before querying: `/admin/users` (search box, status filter, filter-preserving pagination, `AdminTable` empty states, ban state column, link to the profile) and `/admin/users/:id` (account facts, wallet summary, usage totals, the 10 recent sessions with chat-history links, and the ban/unban switch). The switch requires an explicit confirmation whose copy states that the player's existing credentials stop authorizing new user requests and that the wallet is untouched.

## Quota packages and manual wallet adjustments (AC-13/AC-14)

**Packages.** `billing.ts` owns the whole surface; there is no second package table or ledger. `listQuotaPackages()` returns every package (active or not) ordered by `sort_order, id` — the id tiebreak makes the order deterministic across reads, and the public `GET /api/quota/packages` uses the same tiebreak while filtering `active = true`. `createQuotaPackage(input, {actor, requestId?})` and `updateQuotaPackage(id, patch, {actor, requestId?})` share one Zod boundary (`quotaPackageInputSchema`, strict): name trimmed 1–64, `priceCents` an integer ≥ 0 (zero = free package), `points` an integer ≥ 1, `description` ≤ 256 (and nullable: `null` or `''` clears the column, which is exactly what the console's "clear 说明" save sends), `sortOrder` an integer ≥ 0; an undeclared key is a 400, so a client `actor` or a yuan float never reaches the database. The naming rule is enforced case-insensitively inside the mutation transaction under `pg_advisory_xact_lock(hashtext(lower(name)))`, and a collision answers `409 quota_package_name_conflict`. The transaction-scoped advisory lock serialises the read-then-write, so two concurrent creates (or renames) of the same free name cannot both commit: the loser waits, then sees the committed row and is refused. There is still no DB unique index on `name`, so a direct SQL insert bypasses the rule — the application lock, not a constraint, is the enforcement, recorded here rather than hidden.

`updateQuotaPackage` locks the row, compares the parsed patch with the stored row, and returns `{package, changed:false, auditId:null}` with no write when nothing differs; a real change writes only the changed columns and appends `admin.quota_package.update` with `summary {changedFields, from, to}` in the same transaction, so a failed audit insert rolls the update back. `createQuotaPackage` does the same with `admin.quota_package.create`. Availability is `active:false` ("archived"); no service or route deletes a package, because orders reference it. Only later orders read the new price/points: `orders` stores `amountCents`/`pointsAmount` snapshots at creation, so a price change leaves every existing order row byte-identical (tested end-to-end through the public order route).

**Adjustments.** The route reuses `adjustWalletPoints` (five-parameter idempotency, advisory lock on the key, wallet row lock, negative-balance refusal, `audit_pending` intent in the same transaction) instead of building a parallel ledger. The strict body is `{userId, delta, reason, idempotencyKey}`: `userId` must be a UUID, `userId` must exist (`404 admin_user_not_found` is answered before any ledger write, because `wallet_accounts.user_id` is a foreign key), `delta` is a non-zero integer within ±1,000,000, `reason` is required and ≤ 256, and the key is 1–128 characters. A replay with an identical actor/user/direction/amount/reason returns `200` with the original `transactionId`/`balanceAfter`; any difference returns `409 {error:'wallet_adjustment_idempotency_conflict'}` and writes no second transaction. A debit the wallet cannot cover is `409 {error:'insufficient_wallet_balance'}` (the service throws `InsufficientBalanceError`; the message stays `Insufficient balance` so the chat charge path keeps classifying it) — never a dependency outage and never a transaction row. The route finalizes the `wallet_adjustment:<key>` intent after commit; if that settle fails it answers `503 {error:'admin_audit_pending', dedupeKey, transactionId, balanceAfter}` rather than full success, and `GET /wallet/adjustments/:idempotencyKey` reports `{transaction, audit, complete}` for the operator to re-query. `finalize-audit` remains finalize-only.

Concurrency is proven, not assumed: six `-5` adjustments against a balance of 10 leave exactly two transactions and a balance of 0, and an adjustment racing four consumptions always reconstructs the same balance from the ledger with no negative `balance_after`. Rejected conflicts and refusals leave the wallet row and the transaction set untouched.

## Migration 0014/0015 and the capture rule

`0014_character_publishing.sql` adds the pointer, the FK, the partial unique index, the `chat_turn_snapshots(character_id, content_version_id)` index, and tames existing content. `0015_turn_version_pinning.sql` makes `chat_turn_snapshots.client_message_id` nullable (legacy clients cannot send one) and captures model-profile versions so a turn can pin `model_profile_version_id`.

Capture is server-originated, so it records **no human author**: both migrations relax `content_versions_creator_check` / `model_profile_versions_creator_check` additively from "exactly one" to "at most one" creator column, reserving `NULL/NULL` for captured content. Admin-authored rows still name exactly one creator, and `NULL + NULL` stays the only relaxed case. Capture never fabricates evidence: only `status='active'` characters with `published_version_id IS NULL` are captured (application-created draft characters are inactive by design and get no invented publish), each gets exactly one published version whose payload comes from the live display rows plus the newest `character_prompts` row and the bound script card, with `version_no` continuing the existing chain and `content_hash` computed over the stored payload text. A pointer-less live character that already owns a published snapshot adopts it instead of gaining a second one. `/character-capture.ts` and the migration carry copy-identical statements (a test fails if they drift), and `seed()` runs the same unit after inserting characters and model profiles, so `migrate → seed` leaves every seeded character chattable instead of pointer-less. Re-running either path inserts nothing.

Known limit: `0014`/`0015` are hand-written SQL checked into `apps/api/drizzle/` with journal entries but no generated drizzle snapshots (the same practice as `0011`–`0013`), and `config_hash` still has two incompatible recipes — `models.ts` hashes `JSON.stringify(model)`, the `0015` capture hashes `{profileId,provider,modelName,pointsPerCall}` — so the two are not comparable. Neither is unified in this batch.

## Payment reconciliation: AC-12 is BLOCKED

**AC-12 channel reconciliation is NOT implemented, because aggregate payment has no active query (查单) API.** Without a trusted query there is no verified channel result, so the required "verified payment ⇒ idempotent re-credit" path cannot be built honestly and is not built at all. There is no fake or mock channel query, no provider credential in the console, no manual "mark as paid", no arbitrary order-status write and no refund initiation.

What exists is strictly local and read-only: the payment/order/refund rows this service already persisted through the callback path (`GET /api/admin/payments`, `/payments/:id`, `/orders`, `/orders/:id`), plus the pre-existing idempotent credit path the payment callback uses. No new credit, reversal or status-override entry point exists in the console.

**Local state must never be presented as channel evidence.** A stored payment row is what this service recorded, not what the provider reported at query time. The console must not label an order 已支付/已对账 or a refund 已退款 merely because a local row says so when no trusted channel result exists; the honest state is 未确认/无法核对渠道结果, and an unknown channel result is never treated as success. Closing AC-12 requires a real provider query contract (merchant order id, transaction identity, amount, success state, timeout/unknown handling) and is recorded here as blocked rather than approximated.

## Transactions and invariants

Each login inserts a new random 32-byte token and random external subject, stores only SHA256(token), and expires absolutely after eight hours. Resolver checks active account, matching credential version, expiry and revoked state every request. Logout revokes only the current session. Password/reset/disable/recovery/email changes bump version and revoke all sessions; change/reset/recovery restrict as specified (self password change clears restriction).

Account/session changes and successful audit writes share one PG transaction. Audit failure rolls back both. Bootstrap uses fixed advisory lock `(719321,2)`: same normalized protected email is idempotent without replacing credentials, different email or ordinary-only broken state refuses. Actor/target account rows lock in sorted UUID order; current session/version/active/restriction are revalidated under lock. Expensive hashing runs outside locks. Login and current-password mutations verify snapshots then lock/recheck; reset/disable/recovery cannot race stale issuance. Audit sources distinguish account, legacy user, server command and unauthenticated request; credential material is never audit data.

## HTTP and configuration

Finalize-only audit recovery exists for four persisted intents: wallet adjustments, character publish tasks, script publish tasks (both through `publish-tasks/:id/finalize-audit`) and model publishes (`models/:id/finalize-audit`). Each one locks the existing intent, verifies the persisted business result against that original intent (including the recorded actor where the business row carries it, as the wallet transaction does), then only transitions `audit_pending` to committed and appends a separately deduped recovery event under the recovering account. The original actor and summary are never rewritten; none of them re-runs the business operation, rewrites the business row or grants correction authority. A `409` (`character_publish_audit_conflict`, `script_publish_audit_conflict`, `model_publish_audit_conflict`, `wallet_adjustment_audit_conflict`, `audit_recovery_conflict`) means the intent could not be confirmed, so nothing is finalized.

**All four surfaces now offer the same action through one shared control** (`FinalizeAuditAction` + `AUDIT_RECOVERY_COPY` in `app/admin/audit-recovery.tsx` / `audit-recovery-copy.ts`), so the copy cannot drift: 尝试完成审计收尾, a note stating it does not re-execute publish/adjustment and does not rewrite content, configuration, balance or ledger rows, and one sentence for every 409 — 「无法确认该待恢复意图」. The character edit page renders it per `audit_pending` publish task; `/admin/scripts/[id]` renders it per pending cover-publish task from the existing bounded `listPublishTasks('script', id, 5)` read; `/admin/models` renders it per tier whose latest `admin.model.publish` audit is `audit_pending` or an unknown persisted result (the bounded `getModelPublishAuditState` read, also returned as `publishAudit` by the versions route); the wallet page keeps its confirmation step and reuses the same request helper and conflict sentence after a `503 admin_audit_pending`. A `committed` or absent intent shows only the fact and offers no action. There is still no general audit-recovery console and no route that re-runs business logic.

All account bodies are strict Zod objects. Error JSON is `{error:string}`; new boundary errors never log/return driver details. Statuses: invalid 400, unauthenticated/login failure 401, CSRF/restricted/forbidden 403, missing account 404, conflict 409, budget 429, dependency/capacity 503. Restricted code is `admin_password_change_required`.

Character bodies are strict Zod objects. `POST /characters` requires every display field, `starterQuestions`, the five persona fields and an `agentId` from the versioned roleplay agent contract; a client actor, status or `scriptSnapshot` is refused. It creates one `inactive` character with draft version 1 and no published pointer — draft-only: never public, never chattable until published. Content-contract failures answer `400 {error:'character_draft_invalid',issues:[{path,message}]}` from the shared validation module; a malformed id or strict-body violation is `400 admin_input_invalid`. `GET /characters/:id/preview` defaults to the newest draft, then the published version (a draft-only character previews instead of 404), honours an explicit `versionId`, and never returns persona prompt text or chat.

`SafeAdminAccount` has id/email/active/mustChangePassword/isProtected/createdAt/updatedAt. Dates serialize as ISO strings. Cookie `admin_session_v2` is HttpOnly, Strict, Secure in production, Path=/, no Domain, no renewal. Edge middleware only adds admin security/no-store headers; route and page query guards remain mandatory. Sensitive message/session reads return 503 `admin_audit_unavailable` rather than raw text when auditing fails.

The wallet-adjustment `finalize-audit` exists only for identity-migration compatibility: it locks the existing wallet transaction and its `wallet_adjustment:<key>` audit intent, verifies action, object/transaction id, target user, signed amount, reason, balance snapshot and original typed actor equality, then transitions only `audit_pending` to committed and appends a separate recovery event deduped by the original audit id. It never calls the adjustment service, writes `wallet_accounts`, inserts a wallet transaction or changes the idempotency key; complete replays return the stored result, while missing/unknown/mismatched states are 409. It grants no authority to correct money. The publish-task and model variants use the same mechanism for their own persisted intent and additionally cover a publish whose audit settle failed after the business commit (the task keeps `recoveryState='audit_pending'` and the API answers `202`); they never re-publish.

`ADMIN_ORIGIN` must be canonical http(s) origin, no credentials/path/query/fragment; production explicitly requires `https://api.yuemanlou.xyz`, development defaults to `http://localhost:3000`. Host/forwarded-host never determine it. Basic/whitelist production config is removed; unrelated production checks remain. Caddy retains one `reverse_proxy api:3000`, overrides `X-Admin-Client-IP` with `{remote_host}`, and API remains private. Production login trusts only that single net.isIP-valid header; missing/invalid is 503 with no XFF fallback. Development always budgets `local` regardless of spoofed headers. Adding a CDN/proxy requires a fresh trust-boundary review.

## Admin pages

Twenty-two dynamic routes: the nine existing business URLs (`/admin`, `/admin/sessions`, `/admin/orders`, `/admin/payments`, `/admin/wallet`, `/admin/quota-packages`, `/admin/model-usage`, `/admin/blocked-keywords`, `/admin/review-logs`), batch 2's five (`/admin/characters`, `/admin/characters/new`, `/admin/characters/[id]/edit`, `/admin/characters/[id]/preview`, `/admin/sessions/[id]`), batch 3's two (`/admin/users`, `/admin/users/[id]`), the media step's two (`/admin/scripts`, `/admin/scripts/[id]`), and `/admin/login`, `/admin/change-password`, `/admin/accounts`, `/admin/account`. The console layout is a redirect boundary only (missing identity → login, restricted → change-password); every page still calls `requireAdminPageAuth()` before its data query. The browser transport sends same-origin JSON with `X-Admin-Request: 1` and always uses cookies: no Bearer token, no localStorage/sessionStorage and no JavaScript access to the session cookie.

Character and session flows are the batch-2 surfaces: `/admin/characters` is a bounded, searchable page (term over name/agent id/script title + publish-status filter, filter-preserving 上一页/下一页, and two distinguishable empty states — 当前筛选下没有匹配的角色卡 versus 暂无角色卡), and the list keeps publish status, draft divergence and the last publish task as three separate columns plus a readiness warning and the mobile unpublish entry; creation is draft-only with the agent id chosen from the versioned contract; the edit page has four sections (展示资料/角色人设/开场引导/预览与发布), keeps drafts immutable, carries the exact edit baseline, allows the persona to be completed from the draft base, assigns `agentId` once when the stored value is `NULL`, and offers `创建首个草稿` for a character with no version at all. Every one of these controls says it only records the missing audit result, and a 409 is verbatim 「无法确认该待恢复意图」 with no business change.
