# Independent administrator account and authentication boundary

This implements the approved identity boundary and the character content/publish boundary of the web-admin rollout, not a new user-authentication model. Migrations 0013–0017 and historical typed actors remain additive. Miniapp `verifyAuth`, payments and streaming are independent.

Product scope is frozen in `docs/specs/2026-10-31-web-admin-spec.md` (revision 3). Batch 1 shipped the identity/account/session boundary plus the Chinese admin shell; batch 2 ships the character content model (`content_versions` drafts, the single published pointer, immutable publish), the character admin flows, session search/paginated transcript with per-turn version attribution, and the accepted-turn version pin. User operations (search, profile, ban/unban, AC-11) ship in batch 3. Uploads (avatars/covers stay URL text fields), character deletion, order reconciliation, the package/model console, and a general audit-recovery console remain later batches. Implementation status is PARTIAL: local verification uses real PostgreSQL/HTTP/browser, the Node 20 tools image and a local Caddy configuration; production HTTPS/deployment, real miniapp devices, payment channels and LLM providers are not covered.

## Responsibilities and contracts

- `passwords.ts`: async Node scrypt, `scrypt$v1$32768$8$1$<16-byte hex salt>$<64-byte hex output>`, maxmem 64 MiB. Only this exact cost/format is verifiable. Maximum four expensive operations per process; no waiting queue, overload 503. Passwords are 15–128 Unicode codepoints, untrimmed and unnormalized, rejecting common weak values; all credential-setting services share validation.
- `accounts.ts`: normalized-email uniqueness, safe account projection (no hash/version), protected bootstrap/recovery, account lifecycle and current-actor validation. Ordinary creation is strict `{email,password}`, active/restricted/nonprotected. No deletion or reactivation HTTP interface. Only protected self can change email with current password. No self-disable or protected reset/disable by administrators. Recovery explicitly targets an existing UUID and retains protection.
- `authentication.ts`: `AdminIdentity = {adminAccountId,credentialVersion,sessionId,expiresAt,account}`. `loginAdmin({email,password,clientIp})` returns `{token,identity}` internally; HTTP never serializes this internal result. Account mutation services require this identity, not client actors or user IDs.
- `security.ts`: exact Origin + JSON + `X-Admin-Request: 1` on every admin write, private/no-store serializers, safe internal return paths, cookie helpers and persistent login budgets. Email 5/15m, trusted IP 30/15m, global 60/min, consumed atomically in sorted key order before hashing. Denials have positive Retry-After. Stable keys hash email/IP. Cleanup deletes at most 100 expired rows per attempt using indexed expiry/skip-locked; denied attempts saturate counts.
- API `verifyAdminAuth` and SSR `requireAdminPageAuth` use the same token resolver. Full access is default; explicit restricted allowance only for session self-check, own-password change and logout. The change-password page opts in only to display the current identity; no business page or query may use it. SSR returns null without querying protected data on denied/unavailable identity and opts out of caching.
- Old JWT (including whitelist and development bypass), Basic, `admin_session`, and `x-admin-session` never grant admin identity. Historical session creation/revocation remains only for migration regression tests; no legacy resolver is exported or used for authentication.

## Character content versions and the publish boundary

`content_versions` with `entityType='character'` stores every immutable draft and published snapshot as one row (`entityId`, `versionNo`, `status`, `contentHash`, `payload`). `characters.published_version_id` (FK to that table, `0014`) is the single published pointer a chat turn reads; at most one `published` row may exist per `(entity_type, entity_id)` (partial unique index `content_versions_entity_published_unique`). A save inserts a new draft and supersedes the previous draft in one transaction; publish re-validates the bound version, freezes the server-derived `scriptSnapshot` into it, flips display rows and the pointer atomically, and writes a `publish_tasks` row plus an `audit_pending` intent. Unpublish only sets `characters.status='inactive'`: versions, the pointer, tasks and audit stay. Drafts never carry `scriptSnapshot`, and neither the client nor a draft may supply it.

Baselines: a save carries exactly one of `versionId` or `expectedUpdatedAt` (both or neither is `400 admin_input_invalid`); a stale baseline is `409 character_draft_conflict`, never a silent write. `agentId` is system-owned once stored (`409 character_agent_id_system_owned`), and a published character cannot change `scriptId` (`409 character_script_change_requires_new_character`) — re-binding a role requires a new character. The runtime prerequisite for a turn (an enabled model tier with a published model-profile version) is reported as preflight and **never** blocks publishing: a missing model-profile version only means new turns will be refused with `model_profile_unavailable`.

## Derived FastClaw base context (`0016`, `0017`, plan W)

The published PG version is the single persona source. FastClaw keeps its runtime context assembly unchanged (a roleplay turn still reads SOUL.md + IDENTITY.md + USER.md + memory + the output guards), so those three files are a **derived, versioned cache**: publish regenerates them from the version it just activated, writes them through the setup API (`GET`/`PUT /api/agents/{id}/system-files/{name}`, `Authorization: Bearer`, agent id in the path, bounded 5s per request, no retries — the operation is idempotent by content) and records one `agent_context_versions` row. `0016_agent_context_versions.sql` adds that table (unique `(agent_id, content_hash)` so identical bytes never duplicate, `snapshot` = the three rendered files + per-file hashes + character counts, `source` `publish|manual|startup`, nullable `captured_by_admin_account_id`, the originating `content_version_id`/`content_version_no`) and a nullable `chat_turn_snapshots.agent_context_version_id`.

The renderer is server-side and single (`agent-context/render.ts`); `scripts/provision-roleplay-agents.mjs` keeps owning the deploy path and a parity test renders the same characters through both and asserts byte equality, so publish and provisioning cannot drift. Recording is hash-deduped and immutable; the per-agent `b#` badge is a derived ordinal, not an id.

**Which record is current is an explicit pointer, not an ordering.** `0017_agent_current_context.sql` adds `agent_current_context(agent_id PRIMARY KEY, version_id REFERENCES agent_context_versions ON DELETE CASCADE, updated_at)` and backfills one row per agent from the newest capture (replay-safe). Recording is hash-deduped, so publishing A → B → A re-uses the OLD A row with its old `created_at`; `max(created_at)` would then report drift against B while the runtime holds A, no rebuild could clear it, and new turns would pin B. The pointer is written in the SAME transaction as the record and only after the write was verified, so the record insert and "this is what FastClaw holds" can never disagree. Drift, the panel badge (`b#` of the current row), `matchesPublished` and turn attribution all read the pointer; `agent_context_versions` stays append-only history.

**Writes are read back before anything is claimed.** After the three PUTs the sync re-reads all three files and compares exact bytes (and the combined hash). Any mismatch — a PUT that answered 200 without the bytes being visible afterwards — is `failed`/`write_not_verified[:<file>]`, records nothing and never repoints current. `written` is true only when all three PUTs landed; a partial write is `false`.

The read-back proves only that the bytes are visible to the credential in use: FastClaw's setup API scopes both GET and PUT by the authenticated user, so a credential that is not the agent owner writes and reads the same wrong row and still compares equal. Keeping `FASTCLAW_API_KEY` resolvable to the agent's `agents.user_id` is therefore an operational requirement, not something this check can detect.

Syncs are serialized per agent with `pg_advisory_xact_lock(hashtext(agent_id))` and the published source is re-read inside that lock, so two concurrent publishes can never leave a stale current version.

Publish is never failed, rolled back or downgraded by this step: `publishCharacter` returns `baseContext` with `synced | unchanged | pending | failed` (`pending` = FastClaw unreadable, nothing written or recorded, last good record kept; `failed` = a rejected write, a failed read-back, or a failed record — each with its own copy: 写入失败 / 校验失败 / 未记录). The accepted-turn attribution reads the agent's CURRENT recorded version in the accept transaction (one local read, no cross-service call) and stores NULL when nothing was recorded — never backfilled, never inferred. Drift is `GET /characters/:id/base-context` (current record vs the live files: `in-sync | drifted | unavailable | unrecorded`; `unavailable` is never reported as synced) and the rebuild is `POST /characters/:id/base-context` (audited `admin.character.base_context.rebuild`), which overwrites a FastClaw-console hand edit and repoints current even when the bytes match an older row. The admin UI states both facts separately (`基础上下文：b# · 时间 · 状态`, `控制台已被手改，与已发布版本不一致`, `基础上下文未记录`) and never renders persona text or the captured file bytes. `startup` remains a reserved source value with no caller.

## User operations: search, profile and ban/unban (AC-11)

`/users.ts` owns the *player* namespace only. Administrator identity lives in `admin_accounts` inside the independent admin boundary, so a player whose UUID equals an administrator's account id is a different row in a different table: banning that player never disables, resets or logs out the administrator (tested through `verifyAdminAuth` with a real session).

`listAdminUsers({query,status,page,pageSize})` matches one trimmed term three ways — nickname substring (`ILIKE`), openid prefix (`LIKE`, wildcard characters in the operator's term are escaped and therefore literal) and user-id text prefix (a pasted full UUID matches exactly) — and combines it with the status filter. Ordering is `created_at DESC, id DESC`, so a bounded page never reorders between reads. Each row carries `id, nickname, status, createdAt, balancePoints, sessionCount, lastMessageAt`; the aggregates are correlated scalar subqueries in the page statement, so a page of 50 users is one page statement plus one count statement (no N+1), and a player with no wallet row reports `0` rather than a missing value.

`getAdminUser(id)` returns the profile (`nickname, avatarUrl, status, createdAt, updatedAt`, plus a masked `openidPreview` — the raw openid is a login identifier and is never returned), the wallet summary (`balancePoints`, `totalRechargedPoints`, `totalConsumedPoints`, or `exists:false` with zeros), usage totals (`sessionCount`, `messageCount`, `lastMessageAt`, `lastSessionAt`) and the 10 most recent sessions as ids with display context (character name, mode, status, message count, timestamps) so an operator can jump into the existing chat history. No persona prompt, chat body or credential material is selected.

`setAdminUserStatus(actor,id,status,requestId?)` accepts only `active ↔ banned`. One transaction locks the user row (`FOR UPDATE`), and: a missing row is `404`, a malformed id or unknown status is `400` before any write; a status that already matches returns `changed:false` and writes nothing; a real transition updates `users.status`/`updated_at` and appends the audit event within the same transaction — `admin.user.ban` / `admin.user.unban`, `objectType='user'`, `objectId=<player>`, the authenticated administrator as actor, `summary {from,to}` — and a failed audit insert rolls the write back. Because only a real transition can reach the audit insert and the row lock serializes concurrent duplicates into one transition plus no-ops, repeated identical calls add no second audit row without needing a dedupe key; a later ban after an unban is a new event.

Enforcement is the pre-existing user authentication: `verifyAuth` already refuses a JWT whose `users.status` is not `active`, so an already-issued credential stops authorizing new user business requests immediately and works again after the unban. Banning changes no wallet balance, inserts no wallet transaction, and deletes no user, session or message.

Routes: `GET /users` (`q`, `status`, `page`, `pageSize`; unknown status and an over-long term are `400` with Chinese copy), `GET /users/:id`, `PATCH /users/:id` with the strict body `{status:'active'|'banned'}` (a client `actor`, a wallet field or any other key is `400 admin_input_invalid`). Both pages guard before querying: `/admin/users` (search box, status filter, filter-preserving pagination, `AdminTable` empty states, ban state column, link to the profile) and `/admin/users/:id` (account facts, wallet summary, usage totals, the 10 recent sessions with chat-history links, and the ban/unban switch). The switch requires an explicit confirmation whose copy states that the player's existing credentials stop authorizing new user requests and that the wallet is untouched.

## Migration 0014/0015 and the capture rule

`0014_character_publishing.sql` adds the pointer, the FK, the partial unique index, the `chat_turn_snapshots(character_id, content_version_id)` index, and tames existing content. `0015_turn_version_pinning.sql` makes `chat_turn_snapshots.client_message_id` nullable (legacy clients cannot send one) and captures model-profile versions so a turn can pin `model_profile_version_id`.

Capture is server-originated, so it records **no human author**: both migrations relax `content_versions_creator_check` / `model_profile_versions_creator_check` additively from "exactly one" to "at most one" creator column, reserving `NULL/NULL` for captured content. Admin-authored rows still name exactly one creator, and `NULL + NULL` stays the only relaxed case. Capture never fabricates evidence: only `status='active'` characters with `published_version_id IS NULL` are captured (application-created draft characters are inactive by design and get no invented publish), each gets exactly one published version whose payload comes from the live display rows plus the newest `character_prompts` row and the bound script card, with `version_no` continuing the existing chain and `content_hash` computed over the stored payload text. A pointer-less live character that already owns a published snapshot adopts it instead of gaining a second one. `/character-capture.ts` and the migration carry copy-identical statements (a test fails if they drift), and `seed()` runs the same unit after inserting characters and model profiles, so `migrate → seed` leaves every seeded character chattable instead of pointer-less. Re-running either path inserts nothing.

Known limit: `0014`/`0015` are hand-written SQL checked into `apps/api/drizzle/` with journal entries but no generated drizzle snapshots (the same practice as `0011`–`0013`), and `config_hash` still has two incompatible recipes — `models.ts` hashes `JSON.stringify(model)`, the `0015` capture hashes `{profileId,provider,modelName,pointsPerCall}` — so the two are not comparable. Neither is unified in this batch.

## Transactions and invariants

Each login inserts a new random 32-byte token and random external subject, stores only SHA256(token), and expires absolutely after eight hours. Resolver checks active account, matching credential version, expiry and revoked state every request. Logout revokes only the current session. Password/reset/disable/recovery/email changes bump version and revoke all sessions; change/reset/recovery restrict as specified (self password change clears restriction).

Account/session changes and successful audit writes share one PG transaction. Audit failure rolls back both. Bootstrap uses fixed advisory lock `(719321,2)`: same normalized protected email is idempotent without replacing credentials, different email or ordinary-only broken state refuses. Actor/target account rows lock in sorted UUID order; current session/version/active/restriction are revalidated under lock. Expensive hashing runs outside locks. Login and current-password mutations verify snapshots then lock/recheck; reset/disable/recovery cannot race stale issuance. Audit sources distinguish account, legacy user, server command and unauthenticated request; credential material is never audit data.

## HTTP and configuration

Finalize-only audit recovery exists for four persisted intents: wallet adjustments, character publish tasks, script publish tasks (both through `publish-tasks/:id/finalize-audit`) and model publishes (`models/:id/finalize-audit`). Each one locks the existing intent, verifies the persisted business result against that original intent (including the recorded actor where the business row carries it, as the wallet transaction does), then only transitions `audit_pending` to committed and appends a separately deduped recovery event under the recovering account. The original actor and summary are never rewritten; none of them re-runs the business operation, rewrites the business row or grants correction authority. A `409` (`character_publish_audit_conflict`, `script_publish_audit_conflict`, `model_publish_audit_conflict`, `wallet_adjustment_audit_conflict`, `audit_recovery_conflict`) means the intent could not be confirmed, so nothing is finalized. Only the character publish task has a page control (`FinalizeAuditAction` on the edit page); the model route has no UI action because no model console exists yet, and there is no general audit-recovery console.

All account bodies are strict Zod objects. Error JSON is `{error:string}`; new boundary errors never log/return driver details. Statuses: invalid 400, unauthenticated/login failure 401, CSRF/restricted/forbidden 403, missing account 404, conflict 409, budget 429, dependency/capacity 503. Restricted code is `admin_password_change_required`.

Character bodies are strict Zod objects. `POST /characters` requires every display field, `starterQuestions`, the five persona fields and an `agentId` from the versioned roleplay agent contract; a client actor, status or `scriptSnapshot` is refused. It creates one `inactive` character with draft version 1 and no published pointer — draft-only: never public, never chattable until published. Content-contract failures answer `400 {error:'character_draft_invalid',issues:[{path,message}]}` from the shared validation module; a malformed id or strict-body violation is `400 admin_input_invalid`. `GET /characters/:id/preview` defaults to the newest draft, then the published version (a draft-only character previews instead of 404), honours an explicit `versionId`, and never returns persona prompt text or chat.

`SafeAdminAccount` has id/email/active/mustChangePassword/isProtected/createdAt/updatedAt. Dates serialize as ISO strings. Cookie `admin_session_v2` is HttpOnly, Strict, Secure in production, Path=/, no Domain, no renewal. Edge middleware only adds admin security/no-store headers; route and page query guards remain mandatory. Sensitive message/session reads return 503 `admin_audit_unavailable` rather than raw text when auditing fails.

The wallet-adjustment `finalize-audit` exists only for identity-migration compatibility: it locks the existing wallet transaction and its `wallet_adjustment:<key>` audit intent, verifies action, object/transaction id, target user, signed amount, reason, balance snapshot and original typed actor equality, then transitions only `audit_pending` to committed and appends a separate recovery event deduped by the original audit id. It never calls the adjustment service, writes `wallet_accounts`, inserts a wallet transaction or changes the idempotency key; complete replays return the stored result, while missing/unknown/mismatched states are 409. It grants no authority to correct money. The publish-task and model variants use the same mechanism for their own persisted intent and additionally cover a publish whose audit settle failed after the business commit (the task keeps `recoveryState='audit_pending'` and the API answers `202`); they never re-publish.

`ADMIN_ORIGIN` must be canonical http(s) origin, no credentials/path/query/fragment; production explicitly requires `https://api.yuemanlou.xyz`, development defaults to `http://localhost:3000`. Host/forwarded-host never determine it. Basic/whitelist production config is removed; unrelated production checks remain. Caddy retains one `reverse_proxy api:3000`, overrides `X-Admin-Client-IP` with `{remote_host}`, and API remains private. Production login trusts only that single net.isIP-valid header; missing/invalid is 503 with no XFF fallback. Development always budgets `local` regardless of spoofed headers. Adding a CDN/proxy requires a fresh trust-boundary review.

## Admin pages

Twenty dynamic routes: the nine existing business URLs (`/admin`, `/admin/sessions`, `/admin/orders`, `/admin/payments`, `/admin/wallet`, `/admin/quota-packages`, `/admin/model-usage`, `/admin/blocked-keywords`, `/admin/review-logs`), batch 2's five (`/admin/characters`, `/admin/characters/new`, `/admin/characters/[id]/edit`, `/admin/characters/[id]/preview`, `/admin/sessions/[id]`), batch 3's two (`/admin/users`, `/admin/users/[id]`), and `/admin/login`, `/admin/change-password`, `/admin/accounts`, `/admin/account`. The root layout is CSS/metadata only, and login/change-password live outside the private `(console)` group. The console layout is a redirect boundary only (missing identity → login, restricted → change-password); every page still calls `requireAdminPageAuth()` before its data query. The browser transport sends same-origin JSON with `X-Admin-Request: 1` and always uses cookies: no Bearer token, no localStorage/sessionStorage and no JavaScript access to the session cookie.

Character and session flows are the batch-2 surfaces: the list keeps publish status, draft divergence and the last publish task as three separate columns plus a readiness warning; creation is draft-only with the agent id chosen from the versioned contract; the edit page has four sections (展示资料/角色人设/开场引导/预览与发布), keeps drafts immutable, carries the exact edit baseline, allows the persona to be completed from the draft base, assigns `agentId` once when the stored value is `NULL`, and offers `创建首个草稿` for a character with no version at all. Preview is display-only with no chat. Publish/unpublish require an explicit confirmation checkbox, and a task reports `处理中` after 30 s or `已提交，审计待恢复` instead of complete success. `/admin/sessions` filters user/character/mode/status/date range with filter-preserving pagination; `/admin/sessions/[id]` shows metadata plus a paginated transcript where a user turn carries `版本 vN` linking to that version's preview, or `版本未知` when no snapshot exists.

Chinese branding and layout derive from the existing miniapp palette and do not add new business actions or filters beyond these. No memories UI is added (the retired memories PATCH keeps returning 410); message-issue workflow, response comparison and draft trial chat remain excluded, and no upload, character-delete or model-console action exists.

## CLI and validation

Both API/tools packages expose `admin:account = tsx src/server/admin-cli.ts`: `bootstrap --email <email>` or `recover --account-id <uuid>`. Passwords use hidden TTY input or explicit `--password-stdin` (mandatory non-TTY); no password argv/env option. Stdin is bounded and removes only one framing newline. Output is safe identity/status; errors are sanitized; DB import follows argument/secret validation and DB closes on exit. Pure HttpError types are shared without pulling Next into the tools runtime.

All local PG tests/migrations/CLI writes go through `scripts/test-web-admin.mjs`; it verifies exact owned Docker/DB identity before spawning fixed commands. Account suites derive and drop only exact self-created temporary databases within that verified instance. Tests cover concurrent bootstrap/normalization/budgets, protected/restricted access, snapshot races and revocation persistence across fresh connection/module instances, audit rollback, real upgraded-wallet HTTP cutover, cookie/JSON boundaries, and every admin write handler's CSRF/absent-read cache boundary. Batch 2 adds real-PostgreSQL suites for character versioning/publish/unpublish/preview, draft-only creation, first draft, publish preflight, content capture (`character-taming`), session filters and metadata, publish-audit finalization, and accepted-turn pinning (charge/refund at the pinned price, fail-closed rejection, `versionUnknown` for legacy turns). Batch 3 adds real-PostgreSQL user suites: search/status/pagination determinism and aggregates, profile/wallet/usage reads, ban/unban transitions with wallet and admin-identity independence, the audit event per transition, and a banned-then-unbanned JWT driven through the real `verifyAuth` and `/api/me` plus the real admin guard (absent/restricted/CSRF/request-flag) on the new routes. Run them with `pnpm run test:web-admin` — the guarded entry, not a raw vitest invocation — plus `pnpm --filter @juben-sha/api typecheck` and `pnpm run build:api`. Deployment config tests assert private ports and the single proxy override. Password behavior and actual CLI bootstrap/recovery have also run on the Node 20 tools image under 256 MiB/1 CPU against owned PostgreSQL, and the Caddy client-address override has three real local HTTP spoof cases. These are local/practice evidence; passing host tests is not a production deployment claim, and production HTTPS, deployment and restart remain unverified.
