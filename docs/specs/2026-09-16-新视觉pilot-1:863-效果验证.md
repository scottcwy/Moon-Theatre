## 6. C1：素材体积与 GLASS 烘焙

### 6.1 本屏实际使用体积

| 素材 | 代表节点 | 字节数 |
|---|---|---:|
| 剧本 ribbon，2 次复用 | `1:889` | 60,924 |
| 剧本封面右片 | `1:904` | 249,335 |
| 剧本封面左片 | `1:905` | 171,323 |
| 角色卡底图，6 次复用 | `1:963` | 1,457,870 |
| 返回箭头 | `1:1163` | 15,431 |
| Hero 烘焙组 | `1:906` | 1,135,536 |
| **H5 实际使用总计** |  | **3,090,419 B / 2.947 MiB** |

若 Hero 不烘焙、使用 raw `1:909`，素材总量为 `3,122,768 B / 2.978 MiB`。Hero 烘焙减少 `32,349 B / 31.59 KiB`，同时去掉 CSS 对边界和内阴影的近似。

### 6.2 重复卡是否烘焙

- raw 角色卡只存 1 份，被 6 张卡复用；分摊后每卡 `242,978 B`。
- 单张完整烘焙卡 `1:960` 为 `1,372,643 B`。
- 只烘焙第一张的增量约 `1,129,665 B`。
- 6 张全部烘焙相对 raw 复用增加 `6,777,988 B / 6.46 MiB`，增幅约 `464.9%`。
- 结论：**角色卡不整卡烘焙**；GLASS 用 CSS 近似或单独的小型局部资源。

### 6.3 GLASS 单独导出

- `1:964` 导出 PNG 仅 `3,277 B`，但导出结果是近似不透明的深色底，不能作为透明 GLASS 叠层直接复用。
- 因此 GLASS 要么：
  1. 与单次复合组一起烘焙；
  2. 由 CSS 透明层近似；
  3. 重新制作真正透明的局部资源。
- 本屏选择：Hero 随复合组烘焙；角色卡 GLASS 使用 CSS 近似。

## 7. C2：rpx 取整策略

### 7.1 草案

1. 原始事实仍保留 Figma px。
2. 转换公式：`rpxRaw = framePx / 2`。
3. 几何和字体统一使用正整数 rpx：`rpx = Math.floor(rpxRaw + 0.5)`（非负值即四舍五入半上取整）。
4. 描边最小保底 `1rpx`，避免 `<0.5rpx` 被取整成 0。
5. 不建议每个子节点独立 snap 后再重新推导父级；应先 snap 组件边界，再换算内部间距，避免误差累积。
6. 若以取整后值作为设计合同，应反向更新事实层：`更新后的 framePx = rpx × 2`，并记录本轮取整误差。

### 7.2 例证

| 节点 / 属性 | Figma px | 原始 rpx | 取整 rpx | 浏览器误差 |
|---|---:|---:|---:|---:|
| 题目示例 | 50.4875 | 25.24375 | 25 | -0.121875 px |
| 搜索框宽度 `1:885` | 1349 | 674.5 | 675 | +0.25 px |
| 搜索框圆角 `1:887` | 129.1303405762 | 64.5651702881 | 65 | +0.2174 px |
| Hero 组宽 `1:906` | 1355.5 | 677.75 | 678 | +0.125 px |
| 角色卡描边 `1:962` | 3.1779756546 | 1.5889878273 | 2 | +0.2055 px |
| 角色标题字号 `1:957` | 43.9362297058 | 21.9681148529 | 22 | +0.01594 px |

本帧共抽取 1,559 个几何 / 字体 / 描边值，其中 1,141 个不是整数 rpx。`Math.round` 后最大误差为 `±0.5rpx`，即 375 视口 `±0.25px`。证据见 `c2-rounding-examples.json`。

pilot 当前为追求叠图精度，保留部分原始小数 rpx；上述整数化策略是后续 token 化落地草案，尚未反向改动冻结事实层。

## 8. C3：字体方案与 MiSans 对照

### 8.1 结果

| 方案 | 实际平台字体 | 结果 |
|---|---|---|
| 系统栈 | `PingFang SC / PingFangSC-Regular` | pilot 默认，零额外字体字节 |
| MiSans 可选类 | `MiSans / MiSans-Regular` | 通过 `?font=misans` 对照 |
| H5 `Taro.loadFontFace` | `@tarojs/taro-h5@4.2.0` 无实现命中 | 不推荐押注 H5 端 API |

MiSans CDN 对照使用 `MiSans-Regular`（CSS 声明 weight 330）。截图必须显式等待所需字形加载，否则 `font-display: swap` 会让截图错误地停在 fallback，产生“两份截图完全相同”的假结论。

系统字体与 MiSans 像素差：

- 全视口：MAE `2.369`，差异像素 >10 占 `3.52%`。
- 文本核心区：MAE `2.784`，差异像素 >10 占 `4.14%`。
- 差异集中在 Hero 标题 / 描述、顶栏、角色标题和 tab 文案。

### 8.2 建议

- H5 Playground 默认用系统字体栈：零体积、无需远端字体、足以判断布局和色彩。
- 若产品确认必须使用 MiSans：
  - H5 用 `@font-face` 或浏览器 `FontFace`；
  - weapp 另行验证 `Taro.loadFontFace()` 与字体子集体积；
  - 不建议依赖当前 H5 端 `loadFontFace` 实现。
- 证据：`c3-font-evidence.json`、`font-system-vs-misans-diff.png`。
