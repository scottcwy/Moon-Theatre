## 1. 这份 Spec 解决什么

用户结论是「大体和设计稿差异不大，但很多细节不一样」。本 Spec 把它变成可执行的东西：

1. **门禁已可用**：baseline 从 `1500×3247→375×812` 改为 `1500×3247→390×844`，12 帧全部真实出分（此前一直是 `BLOCKED`，等于没有视觉回归保护）。
2. **量化了差距**：初始审计时 12 帧 `0/12` 通过，历史指标见 §3；修复后的最新逐帧结果见 §10.11，不能沿用初始状态判断当前进度。
3. **拆出了根因层次**：哪些是字体管线、哪些是几何常量、哪些是 fixture 失真、哪些是遮罩盲区，见 §4、§5。
4. **给了修复顺序**：先救门禁的可信度，再动 UI，最后逐帧收敛，见 §6。

不做的事：不在本 Spec 内改阈值来换绿灯；不用 `captureOnly` 或缩放比对的结论冒充门禁通过。

## 2. 复现方法

```bash

VISUAL_FIXTURE_API_BASE_URL=http://127.0.0.1:3000 \
  pnpm --filter @juben-sha/miniapp build:weapp:visual-fixture

# 2) 跑门禁（逐帧捕获异常，不会在首帧中断）
pnpm --filter @juben-sha/miniapp test:e2e:visual-frames:second-contract

# 3) 只取帧、不判分（用于单纯采集证据）
VISUAL_FRAME_CAPTURE_ONLY=true pnpm --filter @juben-sha/miniapp test:e2e:visual-frames:second-contract

# 4) 重导基线（可换视口；不传 --target 仍产出 375×812）
node apps/miniapp/scripts/prepare-visual-baseline.mjs --target 390x844
```

产物：`<run-id>/actual/*.png`、`<run-id>/diff/*.png`、`<run-id>/report.json`。

**口径**
- 视口与 baseline 目录只由 matrix 决定（`visual-frame-matrix-second-contract.json`）；package script 已不再重复传 `--baseline`。
- 阈值：未遮罩像素 `MAE <= 16` 且 `|delta| > 10` 的像素比例 `<= 18%`。
- 遮罩按 `1.04` 等比迁移（`375→390`），Home Indicator 段按 `safeArea.bottom=810` 精确取 `y=810..844`。
- `2026-10-19-second-contract/baseline-manifest.json`（375 口径）已被 `baseline-manifest-390x844.json` 取代，仅作追溯保留；`baseline-375x812/` 与 `component-375x812/` 同理。

## 4. 差异清单

严重度：`P0` 决定门禁能否给出有效结论；`P1` 用户一眼能看出的结构偏差；`P2` 细节。

### U-01 字体管线未落地（P0 · 全局）

- **设计口径**：`2026-09-15-月满楼新视觉-设计事实层口径与资产账本.md` §3 冻结 `MiSans×169 · Inter×65 · PingFang SC×10`，§6 下游待办 C3「字体方案二选一」**至今未闭环**。
- **生产现状**：`apps/miniapp/src/app.scss:6` 全局是系统栈 `-apple-system, BlinkMacSystemFont, 'PingFang SC', 'Microsoft YaHei', sans-serif`。`MiSans` 只出现在 `apps/miniapp/src/pages/home/design-pilot/PilotFrame.scss:1`，且是从 jsdelivr CDN `@import` 的 CSS（只对 pilot 页生效，生产路径不可依赖）。
- **影响面**：文字像素。文本占屏约两成，直接解释 chat-empty 的 `21.09%` 变化像素（其余一切几何都对）、以及多数帧 `变化像素 > 70%` 的底噪。
- **判据**：chat-empty 几乎纯排版帧，是最好的一把标尺——字体落地后该帧 `MAE` 与 `变化像素` 必须同时显著下降，而其他帧不应因为这次改动而变差。
- **待决策**：`wx.loadFontFace`（需字体子集化 + 包体预算，注意中文全量 MiSans 数 MB 不可直接进包）vs 承认系统栈并重新标定阈值。**选哪条必须在改代码前写进本 Spec。**

### U-02 首页 hero 卡高度与主按钮形态（P1）

- **实测**：生产 `选择角色` 是**实心枣红填充按钮**，带亮边框，位于 `y 409–446`，整张 hero 卡底部约 `y≈490`；设计稿是**描边按钮**（浅色边线 + 浅字，无极厚重填充），卡底部约 `y≈405`。下游内容整体下移约 `85px`（「选择你喜欢」分隔线随之 `≈437 → ≈518`，目测 ±4px）。
- **位移探针**（绿通道，`y 200..809`，3px 采样，搜索 `dy ∈ [-100,100]`）：`dy=+48` 仅把 MAE 从 `54.62` 压到 `52.58`。→ **不是整体平移，是卡片内部尺寸/间距真的不同**，修间距修不好，必须对齐卡片几何与按钮样式。
- **落点**：`apps/miniapp/src/pages/home/index.scss`（hero/轮播区块）、`packages/miniapp-ui/src/components/**` 中的剧本海报卡。

### U-03 首页剧本列表行（P1）

- **落点**：`apps/miniapp/src/pages/home/index.scss:303`（`.theater-home__script-row`，`height: 196rpx` ≈ `102px`）、`:340`（`.theater-home__script-art`，`width: 56%`）、`:355`（`.theater-home__script-badge`，`background:#7c2742`，贴右上角）、`:366/:374`（`.theater-home__script-desc`，`18rpx` + `-webkit-line-clamp: 4`）。
- **差异**：设计行高约 `110px`（≈`212rpx`）；设计封面占比更小、右侧文字区更宽；设计「类别」标签是浅色浮起内缩小标签，生产是深枣红实心贴角；设计描述是 4–5 行正文，生产只渲染 1 行（见 U-07，属数据失真）。

### U-04 个人页 loading 卡（P0 · 单帧最大偏差之一）

- **落点**：`packages/miniapp-ui/src/components/profile/ProfileLoadingCard.scss:7`（`height: 420rpx`）、`:8`（`margin: 0 32rpx`）、`:10`（`border-radius: 32rpx`）、`:46-49`（月亮 `34rpx` 空心圆）、`:55-58`（指示点只有一个 `10rpx` 圆）；`apps/miniapp/src/pages/profile/index.scss:25-26`（`.profile--loading .profile__loading-card { margin-top: 168rpx }`）、`:352`（另一处 `margin-top: 620rpx`）。
- **差异**：设计卡顶约 `y≈300`，生产约 `y≈150`；设计是月牙，生产是空心圆环；设计三点指示器，生产只有一个点；卡宽/圆角/背景可见比例均不匹配。
- **位移探针**：`dy=-100`（搜索边界）仍未收敛，残余 MAE `39.21` vs 原始 `58.04`。→ 位移能解释一部分，但**卡本身形状也不对**。

### U-05 聊天空态底部栈（P1）

- 该帧 `MAE 10.49` 已达标，失败点是 `变化像素 21.09%`。
- 位移探针 `dy=+88` 使 MAE 从 `11.08 → 7.89`。→ 底部栈（灵感面板 + 输入栏）整体偏低约 `88px`；残余 `7.89` 就是字体/抗锯齿底噪（见 U-01）。
- **落点**：`packages/miniapp-ui/src/components/chat/ChatInputBar.scss:7` — `padding-bottom: calc($space-3 + env(safe-area-inset-bottom, $safe-bottom))`；`packages/miniapp-ui/src/styles/tokens.scss:61` 的 `$safe-bottom: 34rpx`。注意 `34rpx` 在 390 宽下是 `17.7px`，与真机 `safe-area-inset-bottom = 34px` **不等价**，回退值语义可疑，需实测 `env()` 在本构建下的解析结果。
- 同时复核灵感面板底边锚定与输入栏的层叠关系。

### U-06 遮罩挖掉了自定义导航带（P1 · 门禁盲区）

- `approved-masks-second-contract.json` 的 `default` 组遮 `y 0..92`。设计稿的自定义导航标题（`月满楼` / `我的`）在 `y≈62`，生产在 `y≈66`——**这一带的任何偏差永远不会被告警**。
- **修法**：遮罩只到系统状态栏 + 胶囊的真实边界。`systemInfo.statusBarHeight = 47`；胶囊矩形用 `miniProgram.getMenuButtonBoundingClientRect()` 实测后取 `bottom`，把标题带（胶囊下方到内容首行之间）交还给比较。
- 改遮罩属于 Spec 变更，需同步 `2026-10-19-第二份合同UI前端更新Spec.md` §7.3 并记录新的批准理由。

### U-07 fixture 保真度（P0 · 决定门禁是否可信）

- `apps/miniapp/e2e/visual-fixtures/second-contract/home-default.json` 的 `scripts[*]` 只有 `id/title/genre`，**没有 description 文案**；设计稿右侧是 4–5 行正文。→ 首页剧本行右半区结构性不同，**即使 UI 做到 100% 正确也过不了门禁**。
- 当前可见缺口：`home-default`、`quota-package-list`、`share-preview`、`payment-result-success` 四帧都依赖数据填充，需逐帧核对 fixture 是否复刻了设计稿的设计态文案与条目数量。
- **二选一（必须先定）**：(a) fixture 复刻设计稿文案，让像素比较有意义；(b) 对数据驱动文本区加批准遮罩。选 (b) 会削弱门禁价值，倾向 (a)。

### U-10 端口冲突会静默毁掉 fixture 构建（P0 · 门禁可靠性）

- `visual-frames.mjs:390-395` 的 `rebuildWithApiPort()` 执行的是裸 `pnpm exec taro build --type weapp`，`env` 只注入 `NODE_ENV` / `DEV_AUTH_BYPASS` / `API_BASE_URL`，**不带 `VISUAL_FIXTURES=true`**。
- 后果：只要 `3000` 被占（本机有另一项目 vite 占用的历史），runner 换端口后重建一次，就把 §2 里那次 `build:weapp:visual-fixture` 的成果覆盖掉，8/9 退化为 `fixture page not found`，而报错信息完全不提端口。
- **最小修法**：`rebuildWithApiPort` 的 `env` 补 `VISUAL_FIXTURES: 'true'`（与 `build:weapp:visual-fixture` 对齐），或在 `rebuild` 时直接复用该 npm script。
- **临时规避**：跑门禁前确认 `lsof -iTCP:3000 -sTCP:LISTEN` 为空。
