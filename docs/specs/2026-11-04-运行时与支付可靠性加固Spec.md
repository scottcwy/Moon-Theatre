# 运行时与支付可靠性加固 Spec

> 规格状态：`FROZEN` · 需求：`REQUIRED / DECIDED` · 实现：`VERIFIED`
> 日期：2026-11-04 · 审查基线：`main@f49f0ce`
> 本文只冻结修复契约；不代表批准未列出的产品扩张。

## 1. 目标

修复已由代码审查和真实 PostgreSQL 复现的支付、聊天计费、会话并发、内容发布、管理权限、审计、seed、readiness 和生产配置问题，使系统在以下边界上可证明：

- 支付成功能够按商户订单号找到本地订单并只入账一次。
- 同一订单的并发 prepay 不产生多份可支付凭证。
- 已提交完成的聊回复不会因客户端断流而被退款。
- 同一 `clientMessageId` 的首轮并发请求收敛为 `created` 或 `in_progress`，不返回 500。
- 初始化与部署同步不会覆盖运营内容或重置计费配置。
- 管理页面与 API 使用同一管理员身份边界，敏感读取和写入均有审计。
- 内容发布具备真实幂等、并发冲突检测和可恢复状态。
- readiness 区分“角色下架”和“Agent 映射缺失”，并验证实际运行模型。
- 生产配置拒绝弱 JWT secret、危险 fallback 和未知支付 provider。

## 4. 修复不变量

### 4.1 支付与钱包

1. 支付通知以渠道返回的 `out_trade_no` 匹配本地 `orders.merchant_order_no`。不得把同一参数先按 UUID 列绑定。
2. 如果内部 API 需要同时支持订单 UUID 和商户订单号，必须先判断输入身份，再分别查询；禁止在一条 SQL 的 `OR` 中混合两种数据库类型。
3. 每个订单最多有一个可复用的活动支付凭证。并发 prepay 必须收敛到同一支付记录和同一凭证，或明确返回可重试状态，不能生成多份有效凭证。
4. 成功通知、失败通知、mock confirm 和管理员补发复用同一订单级幂等入账边界；最终钱包只入账一次。
5. 订单在 `prepay_created` 之后不得再次创建新的有效 prepay；`credited` 状态不得再次 prepay 或入账。
6. 支付状态未知必须可查询和恢复，不能当作成功、失败或新的 prepay。

### 4.2 聊天回合与扣退

1. 一次生成尝试只有两种账务结果：未提交回复时完成退款，或已提交完整回合时保留一次扣费。
2. assistant、成功 usage、羁绊/关系更新、user turn 状态属于同一已完成回合。任何一项提交后，下游 HTTP 输出失败都不得退款，也不得把 turn 改回 failed。
3. 客户端取消或连接断开时，应尽量取消 FastClaw 上游；即使无法取消，已完成回合仍按成功处理。
4. 一个 generation attempt 最多产生一条成功 usage 和一组幂等扣退流水。断流不得追加第二条 failed usage。
5. `chargeStatus/refundStatus=unknown` 必须由恢复流程对账；恢复完成前不得向用户或后台宣称退款完成。
6. 同一 `clientMessageId` 的会话创建、用户消息创建、租约获取和重试必须保持幂等。会话唯一索引竞争应重新读取并返回 `in_progress` 或既有 turn，不返回 500。
7. 用量记录必须保存 FastClaw 实际返回的模型；业务档位 `modelName` 如需保留，应明确命名为计费配置字段，不能冒充运行模型。

### 4.3 内容、seed 与发布

1. seed 只用于空库 bootstrap。数据库已有剧本、角色、发布版本或托管内容时，普通 `api-seed` 必须拒绝覆盖。
2. seed 不得重置运营修改过的模型价格、套餐价格、推荐状态和上下架状态；默认配置只在缺失时插入。
3. 历史数据清理必须是一次性 migration 或显式危险操作，不得继续挂在常规 seed 中。
4. 同一发布 key 重放必须返回首次发布结果，不能把已发布状态当成“无草稿”错误。
5. 编辑基准检查和写入必须原子化；两个管理员基于同一 `expectedUpdatedAt` 保存时只能一个成功，另一个收到明确冲突。
6. 发布任务、版本激活、审计关联和失败恢复需要可追踪；业务提交成功但审计待恢复时，状态必须可查询且重试不重复激活。

### 4.4 管理权限与审计

1. 管理身份由独立管理员会话（`admin_session_v2`）提供；共享 Basic 门禁已于 Web 后台首批移除，不得重新引入为管理身份来源。
2. 所有 Server Component 页面和 API 必须执行同一管理员身份解析与白名单校验；没有可识别管理员身份时不得查询和渲染订单、支付、钱包、聊天或模型数据。
3. 聊天原文每次读取在返回前必须成功写入访问审计；审计失败返回可识别的依赖故障，不返回正文。
4. 资金调整、内容发布、模型配置发布与套餐变更必须记录操作者、目标、请求/任务标识、结果和变更摘要。
5. 已提交业务但审计失败必须有恢复状态；审计重试不能重复执行资金或发布业务。

### 4.5 readiness 与运行配置

1. Agent 契约、角色映射和可聊天状态分离：
   - 每个契约 Agent 必须有唯一稳定角色映射，即使角色当前 `inactive`。
   - active 角色的 `agent_id` 必须唯一且属于契约。
   - 合法下架不允许让整个服务 readiness 失败。
   - 契约外 active Agent、重复映射或真正缺失的角色行必须失败。
2. 旧链路始终要求默认 Agent 非 roleplay；回滚开关不得出现“ready 但聊天 400”。
3. 所有运行路径必须从 runtime-spec 或 FastClaw 响应校验并记录实际模型；版本要求的 DeepSeek-only 约束必须 fail closed。
4. 生产必须拒绝：
   - 短于明确最小长度的 JWT secret；
   - `FASTCLAW_FALLBACK_ENABLED=true`；
   - 未列入支持集合的 `PAYMENT_PROVIDER`；
   - 空的或明显过弱的管理员会话密钥/密码策略；
   - 非零的 `TEST_USER_INITIAL_POINTS`。
5. fallback 只允许测试或显式开发用途；若收到 fallback done，不得按正常模型成功回合扣点。

## 5. 数据与接口约束

- 优先扩展现有 `payments`、`publish_tasks`、`content_versions`、`admin_audit_logs`、`chat_generation_attempts` 和 wallet 幂等模型，不新建平行账本。
- schema 变更必须 additive、可回滚，并提供真实 PostgreSQL migration 验证。
- 支付、发布和审计接口的新增状态必须能被查询和重试；仅返回 `unknown` 而没有恢复入口不算完成。
- 对外错误继续使用稳定的 `HttpError` 边界，不泄漏 SQL、密钥、prompt、聊天正文或原始渠道报错。
- 现有用户入口、聊天模式、角色 Agent 身份、历史消息和余额不得因修复被删除或重建。

## 6. 非目标

- 不在本规格内完成真实支付渠道的网络联调、退款发起或渠道查单实现。
- 不在本规格内完成 Web 后台全部页面、素材上传、二维码登录或跨 FastClaw 内容版本系统。
- 不改变小程序 UI、文案、Tab 生命周期或视觉基线。
- 不把共享 Basic Auth 升级成新的产品登录体系；只保证它不能单独授权管理员数据。
- 不借修复重写聊天、钱包或后台架构。

| ID | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 使用真实 PostgreSQL 发送已签名成功通知，`out_trade_no` 为 `JB...` 格式 | 能查到订单、入账一次并标记 credited；无 UUID cast 错误 |
| AC-02 | 同一订单并发 20 次 prepay | 最多一条活动支付记录；所有成功响应引用同一凭证，或非首次请求得到明确幂等/冲突结果；不得出现 20 条支付记录 |

| AC-05 | 上游在提交前失败或超时 | 每个 attempt 恰好退款一次；用户净支出为 0；恢复状态可查询 |
| AC-06 | 注入退款 unknown 后执行恢复 | 对账最终完成且无重复退款；恢复前不宣称完成 |
| AC-07 | 同一首轮 `clientMessageId` 20 路并发 | 1 个 created，其余 in_progress/replay；0 个唯一索引 500 |
| AC-08 | roleplay 模式下合法下架一个角色 | readiness 仍为 ready；active 契约外 Agent、重复或真正缺失映射仍失败 |
| AC-09 | `USE_ROLEPLAY_AGENTS=false` 且默认 Agent roleplay=true | readiness 返回 503 |
| AC-10 | runtime-spec 返回 Qwen 或其他未允许模型 | readiness 返回 503；成功请求的 usage 记录实际模型 |
| AC-11 | 纳管后改名、改价格、改套餐上下架并再次执行部署同步 | 运营修改保持不变；普通 seed 拒绝覆盖；显式 bootstrap 仅用于空库 |

| AC-13 | 管理员读取聊天详情、调账、发布内容和修改模型 | 每次操作都有管理审计；审计失败时不返回敏感正文或不宣称完整成功 |

| AC-15 | 两个管理员基于同一 `expectedUpdatedAt` 并发保存 | 一个成功，一个明确 409；无静默覆盖和重复版本号 |
| AC-16 | 生产配置使用 `JWT_SECRET=x`、fallback=true、未知 provider 或非零测试点数 | 启动失败并返回具体缺少/非法配置名 |
