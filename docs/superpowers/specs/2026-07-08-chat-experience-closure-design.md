# Chat Experience Closure Protocol Design

Status: frozen

## Goal

Close the current chat experience bugs as one protocol, not as isolated patches. V1 must stabilize:

- user-visible English/raw errors
- failed-send recovery
- out-of-scope turns
- bond level synchronization
- exact duplicate cleanup
- internal thinking / AI-persona leakage

The design is gap-based: each area records the existing guarantee, remaining gap, target behavior, and tests.

## Resolved Decisions

These decisions came from the accelerated grill. Items marked `[assumed]` were not individually confirmed after acceleration but are required for the frozen spec.

1. **[important] V1 scope**
   - Recommended answer: cover all six bug classes, but do not try to perfectly detect all English, all near-duplicates, or all off-topic intent.
   - Reason: deterministic protocol fixes are verifiable; perfect NLP is not a V1 acceptance target.

2. **[important] Spec structure**
   - Recommended answer: every issue uses `Existing guarantee / Remaining gap / Target behavior / Tests`.
   - Reason: current commits already fix part of the surface, so the spec must preserve existing guarantees and focus remaining work.

3. **[important] Client Message ID**
   - Recommended answer: add `messages.clientMessageId`, generated by the miniapp per send attempt. The user and assistant message for one turn share the same value.
   - Reason: server `messages.id` is unavailable to the client if the stream fails before `done`; `clientMessageId` is the cross-boundary correlation key.

4. **[important] Idempotent retry**
   - Recommended answer: same `clientMessageId` retries return existing results when complete, return `in_progress` only while an unexpired generation lease exists, and re-acquire expired/failed turns for same-ID regeneration.
   - Reason: this prevents duplicate point consumption, duplicate assistant messages, and duplicate side effects without permanently locking crashed or failed turns.

5. **[important] Out-of-scope handling**
   - Recommended answer: generate a draft, run an independent non-streaming scope classifier, then discard the draft and save fallback content when classified `out_of_scope`.
   - Reason: the roleplay output stays pure text; classification metadata stays internal.

6. **[important] Out-of-scope persistence**
   - Recommended answer: save the user message and fallback assistant message, mark both `outOfScope=true` and `excludedFromContext=true`.
   - Reason: history stays visible for the user, but the turn does not affect story context or side effects.

7. **[important] Out-of-scope billing and side effects**
   - Recommended answer: keep the existing pre-consume flow, refund consumed points after `out_of_scope`, do not increment bond, do not extract memories, and do not unlock chat achievements.
   - Reason: the user did not receive an effective story response, and the current cost is not high enough to push this cost to users.

8. **[important] API-owned clean context [assumed]**
   - Recommended answer: product chat context must be built from API-owned saved messages where `excludedFromContext=false`; FastClaw session history must not be the source of product context.
   - Reason: if FastClaw retains the discarded draft under `x-fastclaw-session-key`, `excludedFromContext` is not real.

9. **[important] Error protocol**
   - Recommended answer: stream errors carry stable `code` plus raw `message`; the miniapp maps code to Chinese product copy and never displays unknown raw messages.
   - Reason: raw upstream English is diagnostic data, not UI contract.

10. **[important] Error codes**
    - Recommended answer: V1 codes are `timeout`, `upstream_error`, `upstream_incomplete`, `insufficient_points`, `out_of_scope`, `in_progress`, and `unknown`.
    - Reason: this covers known user-visible English paths without exposing every FastClaw implementation detail.

11. **[important] Failed-send reconciliation**
    - Recommended answer: add a lightweight lookup endpoint by `clientMessageId`, returning `sessionId`, `userMessage`, and optional `assistantMessage`.
    - Reason: it fixes first-message failures where the client never received `sessionId`.

12. **Bond level source of truth**
    - Recommended answer: `/api/characters/:id.relationship` is the initial truth source; `done.bondLevel/bondExp` is only an optional immediate update when synchronous effects are enabled.
    - Reason: async effects intentionally omit bond fields.

13. **Duplicate cleanup**
    - Recommended answer: remove adjacent exact duplicate sentences / paragraphs and exact repeated blocks; do not remove fuzzy-similar language.
    - Reason: exact duplicate cleanup is deterministic; fuzzy deletion can damage roleplay voice.

14. **English cleanup**
    - Recommended answer: fix the five known English/raw error surfaces and known AI-persona/internal-label patterns; do not translate all assistant English.
    - Reason: legitimate story content can contain English names, clues, or quoted text.

15. **Scope classifier failure**
    - Recommended answer: fail open. If the classifier times out or returns invalid output, keep the sanitized assistant draft and log `scope_classifier_failed`.
    - Reason: scope classification is quality control, not safety enforcement.

16. **Model usage status [assumed]**
    - Recommended answer: extend `model_usage_status` with `out_of_scope`, record `pointsConsumed=0`, and include `clientMessageId`.
    - Reason: out-of-scope is not `success`, `failed`, or safety `filtered`.

17. **Client Message ID shape [assumed]**
    - Recommended answer: store as `varchar(128)` instead of UUID, with server validation for length and printable characters.
    - Reason: miniapp runtime support for UUID generation can vary; the value is an idempotency/correlation key, not a database primary key.

18. **Rollout [assumed]**
    - Recommended answer: ship behind normal app release with tests and migration; no feature flag unless implementation uncovers production migration risk.
    - Reason: these are bug-fix semantics, not a product experiment.

## Architecture Boundary

API is the chat state owner. It owns sessions, messages, clean history selection, idempotency, billing, moderation, out-of-scope state, memory, bond, and achievements.

FastClaw is a stateless model executor for product chat. It owns model runtime configuration and generation only. Product chat requests must not send `x-fastclaw-session-key` or rely on FastClaw-persisted session history.

Each generation request sends:

```text
system prompt + recent API-owned clean messages + current user message
```

Only messages with `excludedFromContext=false` can enter this history window.

This spec supersedes the previous FastClaw raw-history investigation item for product chat in the chat output protocol cleanup design.

### Clean History Window

For each product chat generation, the API must query recent clean history from its own database and pass that history to FastClaw explicitly.

Eligible history messages:

- belong to the current authenticated user and current session
- have role `user` or `assistant`
- have `excludedFromContext=false`
- are not part of the current turn (`clientMessageId` differs from the current request)
- for user messages with generation state, belong to a completed turn

Window rules:

- sort eligible messages by `createdAt ASC`
- take the most recent 20 eligible messages before the current turn
- enforce a 6000-character history budget by dropping the oldest complete turns first
- append the current user message separately as the final `user` message

FastClaw adapter input must support:

```ts
Array<{ role: 'system' | 'user' | 'assistant'; content: string }>
```

The adapter must forward exactly the API-built messages array to FastClaw and must not add `x-fastclaw-session-key` for product chat.

### Future Product Architecture

Future product architecture should keep the API as the owner of user-specific agent state. A user's character agent is a product-level instance, not a long-lived FastClaw session or process.

Recommended ownership split:

- **Character Template**: global character definition shared across users, including base identity, public prompt material, script-world binding, default voice, and default runtime policy.
- **User Character Agent Instance**: API-owned record for one user's relationship with one character template. It owns user-specific relationship state, memories, unlocked state, conversation sessions, optional prompt/config overrides, usage policy, and audit history.
- **FastClaw Runtime Executor**: stateless generation runtime for one prepared turn. It receives the API-built `messages` array plus the selected runtime agent/config and returns generated text/events. It must not become the source of product chat history, relationship state, memory, balance, or tenant isolation.

The current V1 schema expresses a user character agent instance implicitly through `userId + characterId` across `chat_sessions`, `memories`, and `relationships`. That is acceptable for V1 because per-user state is limited to conversation, memory, and bond.

If future product requirements need per-user character configuration beyond that implicit key, add an explicit API-owned instance table before pushing state into FastClaw. The likely shape is:

```text
character_templates        # current shared characters / prompts / script binding
user_character_instances   # user_id + character_template_id + per-user role state/config
chat_sessions              # bind to user_character_instance_id
messages                   # bind to session
memories                   # bind to user_character_instance_id or user_id + template during migration
relationships              # bind to user_character_instance_id or user_id + template during migration
```

FastClaw agent selection may later become an API mapping such as `modelTier + characterTemplate + userCharacterAgentInstance -> fastclawAgentId/runtimeProfile`. That mapping should select runtime behavior only. It must not imply that FastClaw owns the product tenant, the user's saved context, or the user's role state.

## Issue 1: User-Visible English And Raw Errors

### Existing Guarantee

- The prompt builder warns the model not to expose system prompt, reasoning, `<think>`, `analysis`, `reasoning`, and AI refusal language.
- The output sanitizer removes common internal tags and some generic AI refusals.
- Timeout and abort strings currently map to approved Chinese copy in the miniapp.

### Remaining Gap

Known user-visible English/raw paths still exist:

- `FastClaw responded with status ...`
- `FastClaw stream ended before completion`
- `FastClaw request failed`
- `Stream error`
- `Stream request failed`
- `Insufficient points`
- model output variants such as `As an AI language model...`
- internal-label variants outside the current sanitizer allowlist

### Target Behavior

- API stream error payload:

```ts
type ChatStreamErrorCode =
  | 'timeout'
  | 'upstream_error'
  | 'upstream_incomplete'
  | 'insufficient_points'
  | 'out_of_scope'
  | 'in_progress'
  | 'unknown';

type ChatStreamErrorEvent = {
  type: 'error';
  code: ChatStreamErrorCode;
  message?: string; // diagnostic only, never directly displayed by miniapp
};
```

- Miniapp maps codes to Chinese product copy:

```text
timeout / upstream_incomplete:
这次回应准备得太久了，或换个更具体的问题再试一次吧

out_of_scope:
这个问题超出了当前角色和剧情能可靠回应的范围。可以换成和角色、线索或当前剧情更相关的问题。

in_progress:
上一条回应还在生成，请稍后再试。

insufficient_points:
点数不足，请先充值后继续。

upstream_error / unknown:
这次回应没能送达，请稍后再试。
```

- The miniapp may keep legacy text matching for `timeout`, `aborted`, and `out_of_scope`, but unknown raw messages must fall back to Chinese generic failure copy.
- Assistant正文 sanitizer expands only known AI-persona and internal-label patterns. It must not translate all English text.

### Tests

- FastClaw incomplete stream returns `code='upstream_incomplete'`.
- FastClaw HTTP failure returns `code='upstream_error'`.
- Missing stream error message maps to `unknown`, not `Stream error`.
- Taro request failure without `errMsg` maps to Chinese generic failure.
- 402 insufficient points maps to `insufficient_points`.
- `getFriendlyStreamErrorMessage` never returns raw unknown English.
- Sanitizer rewrites known AI-persona variants and preserves legitimate English story text.

## Issue 2: Failed Send Recovery And Idempotency

### Existing Guarantee

- The miniapp creates temporary user and assistant bubbles.
- On `done`, it replaces the temporary assistant id with the server assistant `messageId`.
- On `error`, it changes an empty assistant bubble to `[发送失败] ...`.

### Remaining Gap

- If the server saved the assistant but the client timed out before `done`, the UI can show failure while history contains the answer.
- First-message failures are especially bad because the client may not know `sessionId`.
- Retrying the same user action can duplicate user messages, assistant messages, point consumption, and effects.

### Target Behavior

#### Client-generated ID

- The miniapp generates `clientMessageId` per send attempt.
- Request payload adds:

```ts
clientMessageId: string
```

- Server validates length and character set and stores the value on both user and assistant messages.

#### Database

Add to `messages`:

```text
client_message_id varchar(128) nullable
out_of_scope boolean default false not null
excluded_from_context boolean default false not null
generation_status varchar(32) nullable
generation_lease_expires_at timestamp with time zone nullable
generation_attempt integer default 1 not null
```

Add a uniqueness guard for user messages:

```text
unique(session_id, role, client_message_id) where role = 'user' and client_message_id is not null
```

`generation_status` applies to user messages that start a generated chat turn. Valid V1 values are:

- `generating`
- `completed`
- `failed`

#### Idempotent stream behavior

When `/api/chat/stream` receives a `clientMessageId`, lookup is scoped to the current authenticated user. If `sessionId` is provided, an existing turn with that `clientMessageId` must belong to that session. If `sessionId` is omitted, the API may locate the existing turn by current user + `clientMessageId`.

If more than one session for the same user contains the same `clientMessageId`, return a conflict error and log `client_message_id_collision`; the client is expected to generate high-entropy IDs.

State handling:

- user + assistant exists:
  - do not consume points
  - do not call FastClaw
  - do not run effects
  - replay saved assistant as one `delta` plus `done`
  - include `replayed: true`
- user exists, assistant missing, and user `generation_status='generating'` with an unexpired `generation_lease_expires_at`:
  - do not consume points
  - do not call FastClaw
  - return `error { code: 'in_progress' }`
- user exists, assistant missing, and user `generation_status='failed'` or the generation lease has expired:
  - do not insert another user message
  - atomically re-acquire the turn by setting `generation_status='generating'`, extending `generation_lease_expires_at`, and incrementing `generation_attempt`
  - run generation again with the existing user message and same `clientMessageId`
  - use attempt-scoped wallet idempotency keys such as `consume_${userMessageId}_${generationAttempt}` and `refund_${userMessageId}_${generationAttempt}`
  - if another request wins the lease race, return `error { code: 'in_progress' }`
- no record exists:
  - run the normal generation flow

Generation status transitions:

- new generation: create user message with `generation_status='generating'`, `generation_attempt=1`, and a lease longer than the configured FastClaw timeout
- success or out-of-scope fallback saved: update user message to `generation_status='completed'`
- handled upstream/generation failure: update user message to `generation_status='failed'`
- process crash: lease eventually expires; same `clientMessageId` can retry and re-acquire the turn

#### Reconciliation endpoint

Add:

```http
GET /api/chat/messages/by-client-id?clientMessageId=...
```

Response:

```ts
type ClientMessageLookupResponse = {
  sessionId: string;
  clientMessageId: string;
  userMessage: {
    id: string;
    content: string;
    createdAt: string;
    outOfScope: boolean;
    excludedFromContext: boolean;
  };
  assistantMessage: null | {
    id: string;
    content: string;
    mood: string | null;
    createdAt: string;
    outOfScope: boolean;
    excludedFromContext: boolean;
  };
};
```

- Not found returns 404.
- Existing user without assistant returns 200 with `assistantMessage: null`.
- The endpoint must call `verifyAuth` and join through `chat_sessions` so it only returns messages belonging to the current authenticated user.
- If multiple sessions for the same user match the same `clientMessageId`, return 409 and log `client_message_id_collision`.

#### Miniapp recovery

On stream error:

- map error code to Chinese copy
- call by-client-id lookup
- if assistant exists, replace the failed temporary assistant bubble with the server assistant and set `sessionIdRef`
- if only user exists, show `in_progress` copy
- if not found, keep the failure bubble

### Tests

- Duplicate completed `clientMessageId` replays saved assistant without consuming points.
- Duplicate in-progress `clientMessageId` returns `in_progress`.
- Duplicate request does not insert another user message.
- Duplicate request does not run `runChatCompletionEffects`.
- Lookup endpoint returns session/user/assistant for completed turn.
- Lookup endpoint returns session/user/null assistant for in-progress turn.
- Lookup endpoint never returns another user's messages.
- Duplicate stale/failed turn re-acquires the lease and regenerates with an incremented `generation_attempt`.
- Duplicate unexpired generating turn returns `in_progress`.
- Miniapp recovers a failed first-message send using by-client-id lookup.

## Issue 3: Out-of-Scope Turns

### Existing Guarantee

- The miniapp already has approved out-of-scope copy.
- There is no stable API-side classifier yet.

### Remaining Gap

- The AI can jump into plot when the user asks non-story questions.
- A simple input-side rule classifier would be brittle and can misclassify valid roleplay.
- If FastClaw-owned session history remains the product context, discarded drafts may still pollute future turns.

### Target Behavior

#### Classifier

- Run normal generation to produce an assistant draft.
- Run a separate non-streaming scope classifier over:
  - user message
  - assistant draft
  - character identity / prompts
  - script title and world setting
- Classifier returns only:

```ts
type ScopeClassification = 'in_scope' | 'out_of_scope';
```

- On `out_of_scope`:
  - discard the assistant draft
  - save user original text
  - save approved fallback assistant text
  - mark both messages `outOfScope=true` and `excludedFromContext=true`
  - refund consumed points
  - write `model_usage_logs(status='out_of_scope', pointsConsumed=0)`
  - do not extract memory
  - do not increment bond
  - do not unlock achievements / titles
  - stream fallback assistant content and `done { outOfScope: true }`

#### Classifier failure

- If the classifier times out, throws, or returns invalid output:
  - fail open
  - keep the sanitized assistant draft
  - log `scope_classifier_failed`
  - continue normal moderation and effects

#### Context ownership

- Product context for future chat must come from API-owned clean message history.
- Future prompt construction must include only messages where `excludedFromContext=false`.
- FastClaw session history must not be treated as the product context source for this flow.
- Product chat calls must not send `x-fastclaw-session-key`; they must supply recent API-owned clean messages explicitly.

### Tests

- Out-of-scope classification saves user and fallback assistant with both flags.
- Out-of-scope turn refunds points and records `model_usage_logs(status='out_of_scope', pointsConsumed=0, walletTransactionId=null)`.
- Out-of-scope turn does not run memory, bond, achievement, or title effects.
- In-scope turn keeps normal flow.
- Classifier failure fails open and logs `scope_classifier_failed`.
- Prompt/context builder excludes `excludedFromContext=true` messages.
- FastClaw request no longer relies on upstream session history for excluded-context behavior.

## Issue 4: Bond Level Synchronization

### Existing Guarantee

- Character detail reads relationship from `/api/characters/:id`.
- Chat `done` may include `bondLevel/bondExp` when effects run synchronously.

### Remaining Gap

- Chat page initial bond level is hardcoded to 1.
- When `CHAT_EFFECTS_ASYNC_ENABLED=true`, `done` intentionally omits bond fields.

### Target Behavior

- Chat page initial bond level comes from `/api/characters/:id.relationship`.
- `done.bondLevel/bondExp` is treated as optional immediate update.
- If async effects are enabled or `done` omits bond fields, the miniapp refreshes character relationship after `done`.
- No frontend local bond estimation.

### Tests

- Chat page initializes bond level from character relationship.
- Chat page updates from `done.bondLevel` when present.
- Chat page refreshes relationship when `done` omits bond fields.
- Character detail and chat display the same relationship after refresh.

## Issue 5: Duplicate Output Cleanup

### Existing Guarantee

- Sanitizer removes exact repeated halves.
- Miniapp stream client avoids reprocessing full response data after chunk events.

### Remaining Gap

- Adjacent exact duplicate sentences or paragraphs are not removed.
- Near-duplicate cleanup is intentionally not implemented.

### Target Behavior

- Server sanitizer removes:
  - adjacent exact duplicate lines
  - adjacent exact duplicate paragraphs
  - exact repeated blocks
- Sanitizer must not remove:
  - fuzzy-similar roleplay language
  - repeated motifs used for dramatic voice
  - quoted or deliberate repetition

### Tests

- Adjacent identical sentences collapse to one.
- Adjacent identical paragraphs collapse to one.
- Existing repeated-half test remains green.
- Similar but non-identical roleplay phrasing is preserved.

## Issue 6: Internal Thinking And AI-Persona Leakage

### Existing Guarantee

- Prompt guardrails forbid internal prompt, reasoning, `<think>`, `analysis`, `reasoning`, UI metadata, JSON/XML, and generic AI refusal language.
- Sanitizer removes common internal blocks and labeled lines.

### Remaining Gap

- Known AI-persona variants are not all covered.
- Unknown internal labels may survive.
- Output moderation blocked replacement currently contains visible `AI`.

### Target Behavior

- Expand sanitizer known-pattern allowlist for:
  - `As an AI language model`
  - `I am an AI`
  - `I cannot help with that`
  - Chinese variants such as `我是AI`, `我是人工智能`, `我的系统提示`
- If cleaned output is empty or matches AI-persona refusal, replace with in-character fallback.
- Keep sanitizer conservative; do not delete arbitrary English or arbitrary angle-bracket dialogue.
- Replace output-moderation blocked copy with Chinese product text that does not expose raw model/system wording.

### Tests

- New AI-persona variants become in-character fallback.
- Legitimate English names/clues remain.
- Internal label variants are removed only when they match known internal patterns.
- Output moderation blocked content no longer displays raw `AI` wording if product copy changes.

## Observability

### Target Events / Fields

- `clientMessageId` on:
  - chat latency logs
  - model usage logs
  - failed / replayed stream logs
  - scope classifier logs
- Error code on:
  - stream error events
  - model usage logs when applicable
  - frontend debug logs if enabled
- New log events:
  - `chat_stream_replayed`
  - `chat_stream_in_progress`
  - `scope_classifier_failed`
  - `chat_turn_out_of_scope`

### Tests

- Failed FastClaw generation logs code.
- Out-of-scope flow logs `clientMessageId`.
- Replayed idempotent request logs replay and does not insert model usage twice.

## Data And Migration

Required schema changes:

- `messages.client_message_id varchar(128)`
- `messages.out_of_scope boolean default false not null`
- `messages.excluded_from_context boolean default false not null`
- `messages.generation_status varchar(32)`
- `messages.generation_lease_expires_at timestamp with time zone`
- `messages.generation_attempt integer default 1 not null`
- partial unique index for user messages by `session_id + role + client_message_id`
- `model_usage_status` enum adds `out_of_scope`
- `model_usage_logs.client_message_id varchar(128)` [assumed]
- optional `model_usage_logs.error_code varchar(64)` [assumed]

Migration must backfill existing messages:

- `out_of_scope=false`
- `excluded_from_context=false`
- `client_message_id=null`
- `generation_status=null`
- `generation_lease_expires_at=null`
- `generation_attempt=1`

## Non-Goals

- Do not implement perfect semantic off-topic detection.
- Do not translate all assistant English.
- Do not remove fuzzy-similar roleplay repetition.
- Do not expose FastClaw raw errors to users.
- Do not build a queue or long-polling job system in V1.
- Do not create a `chat_turns` table in V1.
- Do not change model tier pricing.

## Rollout And Rollback

- Ship with database migration and targeted tests.
- Rollback must tolerate nullable `client_message_id`.
- If scope classifier causes regressions, disable classifier call and fail open while retaining message fields.
- If idempotent replay causes regressions, frontend can stop sending `clientMessageId`; nullable schema keeps old behavior available.
